## Q1. URL Shortener 的兩個核心 API 是什麼？這兩個 API 的流量特性差很多——你會怎麼利用 load balancer 的路由策略區分處理？

### 你的答案
> 1. create short url
> 2. redirect
>
> 分成 read path (redirect), write path (create short url)
> Heavy read, multiple backend services alongside with cache, so the same request payload would not touch the database.

### 評估
**正確的部分**：
- 正確拆出兩個核心 API（create / redirect），且抓到 redirect 是 read-heavy、create 是 write-heavy 的核心不對稱性，這是這題最重要的觀察
- 提到用 cache 擋掉大部分 read 請求,避免打到 DB,方向正確

**不足的部分**：
- **沒有真正回答「load balancer 路由策略」**：題目問的是 LB 層面怎麼區分處理,你回答的是「有 cache」，但沒說 LB 怎麼把兩種請求分流到不同的 backend pool
- 遺漏一個關鍵矛盾：要依據 API path（`/api/shorten` vs `/{shortcode}`）把流量導到不同 backend,**必須用 Layer 7 load balancer**（要解析 request 內容才能依路徑分流),而不是 Day 2 教材中效能較好的 Layer 4。這是一個值得在面試中主動點出的 trade-off：「用 L7 犧牲一點效能,換取依路徑分流、各自獨立擴展的彈性」
- 沒提到兩個 backend pool 可以**各自獨立水平擴展**（primer 強調的 application layer 拆分核心價值）——redirect pool 可能需要遠多於 create pool 的機器數量
- 沒提到極端情況下,熱門短網址甚至可以在 **CDN/edge 層**直接快取 redirect 回應,連 application server 都不用打到

### 建議答案
> 兩個核心 API：**Create（POST /api/shorten）** 與 **Redirect（GET /{shortcode}）**。
>
> 這兩者流量特性差異極大：redirect 是 read-heavy（讀寫比可能到 100:1 以上）、延遲敏感（使用者點擊後要立刻跳轉）；create 是 write-heavy 但頻率低、可以容忍稍高延遲。
>
> Load balancer 策略：
> 1. 用 **Layer 7 load balancer** 依 request path 分流——`/api/shorten` 導到 create service pool，`/{shortcode}` 導到 redirect service pool。犧牲 L4 的效能優勢,換取依路徑路由與兩個 pool 獨立擴展的彈性
> 2. **Redirect pool** 因為 read-heavy，可以搭配 cache（Redis）擋掉大部分請求不落地到 DB,同時這個 pool 可以水平擴展遠多於 create pool 的機器數
> 3. **Create pool** 機器數可以少很多，但要注意 ID 產生的唯一性（如果多台同時產生短碼,要有機制避免衝突,例如 pre-allocated ID range 或 distributed ID generator）
> 4. 進階：極熱門的短網址可以在 CDN/edge cache 直接處理 redirect,完全不經過 application server

## Q2. 為什麼這個系統的 application server 必須是 stateless？如果不是會發生什麼問題？

### 你的答案
> stateless 可以保證狀態不儲存在某一台的 application server，所以可以利用 load balancer 做 horizontal scalibility。
> 不是可能還會需要使用 shared session storage 或 sticky session 避免狀態遺失

### 評估
**正確的部分**：
- 核心邏輯完全正確，且跟 primer 原文的論述一致：stateless → 才能自由水平擴展；若非 stateless → 需要 sticky session 或 shared session storage
- 這題回答簡潔到位,不需要大改

**可以加強的部分**（非錯誤,是讓答案更有深度）：
- 可以補充 sticky session 的代價：它會降低 load balancer 的路由自由度（某個 client 被綁死在某台 server),萬一那台 server 掛掉,狀態就真的遺失——這是為什麼業界更偏好 shared session storage（Redis/Memcached）而非 sticky session
- URL Shortener 本身這題沒有明顯的「使用者 session」概念（除非有登入功能記錄使用者建立的短網址列表），可以主動點出「這題本身 stateless 更多是為了讓 redirect/create 兩個 pool 能自由水平擴展,而非 session 管理」，展現你知道這個原則不是無腦套用

### 建議答案
> Stateless 代表任何一台 application server 都能處理任一個請求,不依賴前一次請求留在特定機器上的狀態。這樣 load balancer 才能自由地把請求分配到任何一台健康的機器,並且可以隨流量增減任意加減機器（horizontal scaling）。
>
> 如果 server 是 stateful（例如把使用者的 session 存在本機記憶體),會遇到兩個問題：
> 1. 要嘛用 **sticky session**——同一個 client 綁死在同一台 server,但這台掛掉狀態就遺失,而且降低 LB 的負載平衡自由度
> 2. 要嘛用 **shared session storage**（Redis/Memcached）——把狀態抽出來給所有 server 共用,這其實就是把系統改回 stateless 的做法
>
> 對 URL Shortener 這題來說,兩個核心 API（create/redirect）本身不太需要 session,stateless 的價值主要在於讓 create pool 跟 redirect pool 都能各自任意水平擴展。

## Q3. 要不要拆成 microservices（create / redirect 拆成兩個服務)？用今天學到的 trade-off 說明理由。

### 你的答案
> 可以拆成 microservice
> pros: 將責任清楚劃分，可以建立多個 建立短網址的 微服務 做為負載平衡
> cons: 系統變複雜，需要另外建立 healthy check 以及 monitoring，issue tracking 也變複雜。

### 評估
**正確的部分**：
- Cons 完全正確且踩到 primer 原文重點：monitoring、health check、維運複雜度增加,是 microservices 最實際的代價

**不足/需要修正的部分**：
- **Pro 舉例抓錯重點**：你說「可以建立多個建立短網址的微服務做為負載平衡」——但 create（write path）流量小,不太需要靠拆 microservice 來多開機器;真正該多開機器水平擴展的是 **redirect（read path）**。這題的核心 pro 應該是「兩個服務因為流量特性完全不同,拆開後可以**各自獨立擴展**,不會因為 redirect 需要 100 台機器而被迫也把 create 開到 100 台」
- 沒有提到「過度工程」的風險：這是一個只有 2 個 API 的簡單系統,**是否值得一開始就上真正的 microservices**（獨立 repo、獨立部署、service discovery)？更務實的中間方案是「同一份程式碼,但 create 跟 redirect 部署成兩個獨立的 deployment group/pool,各自可以獨立擴展,但共用程式庫」，等到團隊規模或複雜度真的需要時,再演進成真正的 microservices。這種「先分池,不先拆服務」的漸進思路，在資深工程師面試中是加分點,展現你不會為了教科書式正確而過度設計

### 建議答案
> 傾向**先用「獨立部署池（deployment pool),不急著拆成真正 microservices**」。
>
> Pros（拆開的價值）：
> - 兩個 API 流量特性差異極大（redirect read-heavy、create write-heavy),拆開後可以**各自獨立擴展**——redirect pool 開多台因應高流量,create pool 維持少量機器,不會互相拖累
> - 職責清楚劃分,符合 single responsibility principle,未來要換 team owner 或個別優化（例如 redirect 想上更激進的 cache 策略）也互不影響
>
> Cons（拆開的代價）：
> - 需要額外的 health check、monitoring、service discovery（primer 提到 Consul/Etcd/Zookeeper）
> - 部署與維運複雜度提升,issue tracking、debugging 跨服務追蹤變困難
>
> 折衷方案：這題規模不大（只有 2 個 API),**不一定要上完整 microservices 架構**（獨立 repo + service discovery）,可以先用同一份程式碼、依 path 分流到兩個獨立 deployment pool（各自可以水平擴展),等系統規模、團隊規模真的成長到需要獨立維運時,再演進成真正的 microservices。這樣可以避免過早引入 primer 提到的維運複雜度成本。

## 總評

三題核心邏輯方向都對,基礎穩固。主要待加強：
1. **從「概念知道」進到「具體機制」**——例如 Q1 知道要分流,但沒講到 L7 路由的技術細節與代價
2. **抓住系統的不對稱性,並用它反推設計取捨**——Q3 的 pro 沒抓到「redirect 需要獨立擴展」這個最強的論點
3. **展現資深工程師的「不過度設計」判斷力**——Q3 可以主動提出比全套 microservices 更務實的中間方案，這在面試中是加分細節
