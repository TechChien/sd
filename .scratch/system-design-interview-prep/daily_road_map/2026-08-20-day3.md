## Q1. URL Shortener 的核心資料表要存什麼欄位？你會選 SQL 還是 NoSQL？為什麼？

### 你的答案
> ```
> {
>   short_code, long_url, status: active|expired|deleted,
>   alias, owner_id, createdAt, updatedAt, redirect: 302|307
> }
> ```
> SQL，因為 schema 結構固定，可以加上 index 提高查詢效率。

### 評估
**正確的部分**：
- 欄位設計完整且務實：`status`（軟刪除/過期）、`alias`（自訂短碼）、`owner_id`（歸屬）、`redirect: 302|307`（這個細節很好——區分 302 temporary/307 permanent redirect 會影響瀏覽器與 CDN 是否快取跳轉結果，很多人會漏掉這點）
- SQL 的理由（schema 固定 + index）本身沒有錯

**不足的部分——這題有個重要的「反向陷阱」**：
- system-design-primer 對 **Key-Value Store** 的定義就是「abstraction: hash table，提供 O(1) 讀寫」。`short_code → long_url` 這個查詢**本質上就是教科書等級的 key-value 查詢場景**——你只用一個 key 查一個 value，完全不需要 join。你選 SQL 的理由「schema 固定」沒錯，但沒有先意識到「這題其實是 NoSQL/KV store 的典型應用」，等於少了一半的分析
- 更完整的回答應該是「兩者都能做，關鍵看瓶頸在哪」：
  - 若最大瓶頸是 **redirect 的高吞吐讀取**（Day 2 已定調 redirect 是 read-heavy），DynamoDB/Redis 這類 key-value store 對 `short_code` 單鍵查詢的 O(1) 讀取與高 IOPS 更有優勢
  - 若考量 `owner_id` 查詢（「我建立過哪些短網址」）、`status` 篩選、之後可能要做分析報表，SQL 的 index + 查詢彈性更好
  - 務實答案：**核心 redirect 熱路徑用 key-value store（或 SQL + 強力 cache 頂住）**，`owner_id`/`status` 這類管理型查詢可以另外維護一份 metadata table（SQL），兩者並存
- 沒有明確提到要對 `short_code`、`alias` 建 **unique index**

### 建議答案
> 欄位設計沿用你的版本（已經很完整），額外補充索引：`short_code` 與 `alias` 都要建 **unique index**，`owner_id` 建一般 index 支援「使用者的短網址列表」查詢。
>
> 資料庫選型上，這題有個值得主動點出的觀察：`short_code → long_url` 這個查詢完全符合 system-design-primer 對 **Key-Value Store**（hash table 抽象、O(1) 讀寫）的定義，是教科書等級的 KV 場景，不需要任何 join。所以嚴格說，NoSQL/KV store（如 DynamoDB）對這條熱路徑（redirect）更貼合。
>
> 但如果同時要支援 `owner_id` 查詢、`status` 篩選、未來的後台管理/報表需求，SQL 的 index + 查詢彈性更好。務實做法：**redirect 熱路徑可以用 SQL + 強力 cache（Redis）頂住，不一定要換成 NoSQL**——因為 primer 也強調「先用手上熟悉、複雜度低的方案（SQL+cache），除非真的量體大到 SQL scaling 明顯撐不住，才引入 NoSQL」。回答「SQL，因為 schema 固定」沒錯，但要先展現你意識到這題的另一面（KV store 更貼合），再說明你為什麼仍選 SQL，這樣的論述才完整。

## Q2. 短碼怎麼產生，才能在多台 write server 同時運作下保證唯一、且不需要每次都查一次 DB 確認是否重複？

### 你的答案
> 使用 RNGPCS 產生 16bit，再透過 Base62 產生唯一值。

### 評估
**這題有實質問題，需要修正**：

1. **Keyspace 太小**：16 bit 只有 65536 種組合。依生日悖論（birthday paradox），大約產生 **300 個左右**短碼就有 50% 機率撞號——這對任何實際規模的系統都完全不夠用。
   > 來源：[system-design-primer / Pastebin 設計](https://github.com/donnemartin/system-design-primer/blob/master/solutions/system_design/pastebin/README.md) 採用 **MD5 hash 取前 7 碼 Base62 編碼**，等於 `62^7 ≈ 3.5 兆` 種組合，用來應付「3 年 3.6 億筆短網址」的量級。你的 16 bit 遠遠不足。

2. **「不需要每次查 DB 確認」這個前提，其實連 primer 的方法都做不到**：primer 原文寫的是「若產生的 url 不唯一，就再產生一次」（"If the url is not unique, it generates another url"）——**這代表即使用 MD5+Base62,系統仍然會查 DB 檢查碰撞**，只是碰撞機率極低（keyspace 夠大),所以檢查成本可以接受。所以你題目設定的「完全不查 DB」這個目標，用純 random/hash 的方法是做不到「保證」的，只能做到「機率極低」。

3. **要做到真正「不需要每次查 DB 就保證唯一」，需要另一類方法**（primer 的 pastebin 文件沒有涵蓋這個，屬於業界常見但非 primer 來源的模式，這裡明確標註來源差異）：
   - **Key Generation Service（KGS）**：預先產生一批唯一短碼存起來,每台 write server 啟動時**認領一段 range**（例如 server A 拿 1,000,000–1,999,999,server B 拿 2,000,000–2,999,999),各自從自己的 range 裡取號,天生不會跟其他 server 衝突,完全不用查 DB
   - **Distributed ID Generator（如 Twitter Snowflake）**：ID 由 `timestamp + machine_id + sequence number` 組成,不同機器產生的 ID 結構上保證不重複,再把這個數字 base62 編碼成短碼

### 建議答案
> 若堅持用「random + base62」，keyspace 至少要到 base62^7（≈3.5 兆),對應 primer 的 Pastebin 設計：對 IP+timestamp（或亂數）做 MD5 hash,取前 7 碼做 base62 編碼。但要誠實說明：**這個方法仍需要查 DB 檢查碰撞**（碰撞時重新產生一次),只是因為 keyspace 夠大,碰撞機率趨近於 0,檢查成本可忽略,不是「完全不查」。
>
> 若題目真的要求「多台 write server 完全不需要查 DB 就保證唯一」，正確做法是換成：
> - **Key Generation Service**：中心化服務預先產生一大批唯一短碼,每台 write server 認領一段不重疊的 range 存在本機,取號時只從自己的 range 拿,天生無衝突
> - 或 **Snowflake-like distributed ID generator**：`timestamp + machine_id + sequence`，結構上保證跨機器唯一，再 base62 編碼

## Q3. 資料量成長到很大時，你會選 Sharding 還是 Federation？依據什麼欄位 shard？

### 你的答案
> Sharding
> Pros: Scalability, Availability, Fault tolerance
> Cons: Complexity (partition mapping, routing to different db instances, non-uniform), Analysis (aggregate data from different instances)
>
> 依據 short_code 欄位經過 Hash mod 來作為分散至 sharding 的 key
> 備註：Federation 主要整合異質資料統一窗口

### 評估
**正確的部分**：
- 選 Sharding 的方向正確——這題資料本質上是單一 entity（短網址記錄），不是「多個功能領域各自一個 DB」的情境,不符合 Federation 的適用場景
- Pros/Cons 抓得精準，且踩到 primer 原文重點：rebalance/partition mapping 複雜度、跨 shard 分析困難，這兩點是 primer 明確列出的 sharding 缺點
- 用 `short_code` hash 決定 shard，方向正確——因為所有查詢幾乎都是「拿 short_code 查」，用它當 shard key 可以讓單次查詢只打一個 shard，不需要 scatter-gather

**需要修正的部分**：
- **Federation 的定義理解反了**：你說「Federation 主要整合異質資料統一窗口」，但 primer 原文是相反的——Federation 是**把同一個資料庫依「功能」拆成多個獨立資料庫**（例如 forums DB、users DB、products DB 分開），是「拆分」不是「整合統一」。它適用的情境是「你的系統有多個功能領域,各自資料量還不到需要 shard 的程度,但想先降低單一 DB 的壓力」。URL Shortener 這題本身只有單一功能領域（短網址記錄本身),沒有多個功能領域可以拆,所以 Federation 確實不適用——但理由不是你講的「整合異質資料」，而是「這裡沒有多個功能領域需要分開」。
- **Hash mod 有一個經典陷阱值得主動提出**：單純 `hash(short_code) mod N`，當你要增加/減少 shard 數量（N 改變）時，幾乎所有資料的映射都會變,需要大規模搬移資料。Primer 原文明確提到這個問題,並指出 **consistent hashing** 可以緩解 rebalance 的複雜度（增減節點時只有一小部分 key 需要重新映射）。這題如果主動提到「用 consistent hashing 而非單純 hash mod N」，是很加分的細節。

### 建議答案
> 選 **Sharding**。這題資料本質上是單一功能領域（短網址記錄本身），沒有多個功能領域可以拆分，所以 Federation（依「功能」拆分成多個 DB,如 forums/users/products 分開)不適用——不是因為 Federation 用來「整合異質資料」，相反,Federation 是把單一 DB 依功能拆開,而這裡沒有多個功能可拆。
>
> Shard key 用 `short_code` 的 hash 值，這樣「拿 short_code 查 long_url」這個最主要的查詢只需要打一個 shard，不需要 scatter-gather 所有 shard。
>
> 但要注意：單純 `hash(short_code) mod N`，當 shard 數量 N 改變時（擴容/縮容），幾乎所有 key 的映射都會跟著變，需要大量資料搬移。應該改用 **consistent hashing**（primer 原文明確提到這點來緩解 rebalance 問題），增減節點時只有一小部分 key 需要重新分佈，其餘不受影響。
>
> Cons 保留你原本抓到的：partition mapping/routing 複雜度、跨 shard 分析困難（例如「全站短網址總數」這類聚合查詢需要跨 shard 彙總）。

## 總評

Q1、Q3 方向大致正確，細節需要補強（KV store 適配性的反思、Federation 定義修正、consistent hashing）。**Q2 是今天最需要注意的一題**：keyspace 大小的量級估算錯了兩個數量級以上，而且「不查 DB 就能保證唯一」這個前提本身，連 primer 的方法都做不到——這反映出估算數量級（back-of-envelope calculation）與釐清「機率極低」與「保證」的差異，是接下來要刻意練習的重點。
