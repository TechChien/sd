# Day 4 — Caching 策略（Cache-aside / Write-through / CDN）套用於 URL Shortener

Date: 2026-08-21

---

## Q1. Redirect（read path）你會選哪一種 caching 策略？為什麼？

### 你的答案
> 實際上短網址系統創建後就比較少機會做修改，所以使用 write through，在創建短網址的時候就寫入 cache 同時更新 db，並藉由 TTL 的方式讓 cache hit rate 提高。
>
> Cache-aside 如果 cache miss 會需要 read cache(miss) → read db → write cache → return，延遲增加
> Write-behind 是 write path 加速
> Refresh-Ahead 在快取快過期先刷新常被讀取的項目，適用於熱短網址的 case

### 評估
**正確的部分**：
- 四種策略的特性都描述正確，尤其抓到「write-through 可以避免 redirect 第一次讀取時的 cache miss」這個關鍵優勢——因為建立時就已經寫進 cache，之後任何一次 redirect 都不會踩到 cache miss 的延遲，這是很細緻的觀察
- 正確識別 Refresh-Ahead 適合熱門短網址的情境

**需要補強的部分**：
1. **漏掉 write-through 在 primer 原文明確列出的一個缺點，而且剛好命中這題**：primer 原文寫「Most of the data written might never be read」——短網址系統的存取模式通常是 **長尾分佈**（少數短網址被瘋狂點擊、大多數建立後幾乎沒人點,甚至完全沒人點）。如果每個建立的短網址都無條件寫進 cache,等於幫大量「永遠不會被讀」的資料佔用 cache 記憶體,這正是 primer 點名的 write-through 缺點。你有提到用 TTL,但 TTL 在原文中是用來**緩解**這個問題（讓沒人讀的資料到期後自然被清掉),而不是完全消除——這個因果關係值得在面試中講清楚,展現你知道自己選的策略有什麼代價、又怎麼緩解
2. **Write-through 的定義細節**：Primer 原文是「應用程式把 cache 當成主要資料儲存,cache 負責同步寫回 DB」——也就是 app 只跟 cache 溝通,由 cache 負責寫 DB。你描述的是「建立時同時寫 cache 跟寫 DB」，這其實比較接近 **dual write**（app 自己分別寫兩個地方),跟教科書定義的 write-through（app 只寫 cache,cache 代理寫 DB）不完全一樣。這在面試中不是致命錯誤,但用詞要精確——如果你的實作是 app 自己寫兩邊,那該講的風險是「兩邊寫入不是原子操作,要注意寫入順序與失敗處理」（這點延伸到 Q2）

### 建議答案
> 選 **Write-through（或更精確地說：建立時採 dual write，同時寫入 DB 與 cache)**，因為短網址系統的存取模式是「一次建立、大量重複讀取」，在建立當下就把資料放進 cache,可以讓後續所有 redirect 都直接命中 cache,完全避免 cache-aside 那種「第一次讀取必然 miss」的延遲。
>
> 但這個策略有一個 primer 原文點名的代價：**短網址存取通常是長尾分佈**，大多數建立的短網址其實很少被點擊、甚至完全沒人點,無條件把它們寫進 cache 等於浪費記憶體在「永遠不會被讀」的資料上（primer 原文："Most of the data written might never be read"）。緩解方式是幫 cache 設定合理的 **TTL + LRU/LFU eviction policy**，讓冷門短網址自然被淘汰出 cache,只留下真正被重複存取的熱門項目。這樣仍然享有「建立時就快取」的低延遲優勢,又不會讓 cache 被大量冷門資料塞滿。

## Q2. Create（write path）新建立的短網址，需要立刻寫進 cache 嗎？

### 你的答案
> 同時寫進 cache，可以降低延遲。因為短網址是 read:write = 1000:1 的服務（read heavy）

### 評估
**正確的部分**：
- 用讀寫比例（read-heavy）當作決策依據，方向正確，跟 Q1 的推論一致

**遺漏的部分**：
- **沒有處理「同時寫兩個地方」的一致性風險**：如果 app 分別寫 DB 跟 cache，這兩個寫入不是原子操作——萬一寫 DB 成功、寫 cache 失敗（或反過來),系統會進入不一致狀態。**寫入順序很關鍵**：應該**先寫 DB（source of truth），成功後才寫 cache**。如果順序反過來（先寫 cache），一旦接下來寫 DB 失敗，cache 裡會有一筆「DB 裡根本不存在」的短網址,使用者可能因此被導向一個資料庫端已經失敗、不該存在的連結,這是更嚴重的錯誤情境
- 進一步：若寫 cache 失敗（DB 已成功),不需要整個 request 失敗——因為 cache-aside 的邏輯仍然存在:下一次 redirect 讀取時 cache miss,自然會從 DB 補回來。這代表「dual write 失敗」不必是災難,只要 DB 是唯一真相來源,cache 沒寫成功頂多讓「第一次讀取」多一次 cache miss 延遲,不影響正確性

### 建議答案
> 是,同時寫進 cache 可以避免 Q1 提到的「第一次 redirect 就 cache miss」的延遲，符合 read-heavy 的存取模式。
>
> 但要注意寫入順序：**必須先寫 DB（source of truth），DB 寫入成功後才寫 cache**。如果順序反過來,一旦後續 DB 寫入失敗,cache 裡會出現一筆資料庫端不存在的「幽靈短網址」，使用者可能被導到一個系統認定不存在的連結。
>
> 另外，若 DB 已寫入成功但寫 cache 這一步失敗，不需要讓整個 create request 失敗——因為之後任何一次 redirect 讀取碰到 cache miss，本質上就會退化成 cache-aside 行為（讀 DB、補回 cache），只是第一次讀取會多一點延遲，不影響正確性。

## Q3. `status: expired` 狀態改變，但 cache 還是舊資料——invalidation 怎麼處理？

### 你的答案
> 使用排程固定檢查 expiredDate < now，先 invalidate cache 避免 user 查詢到過期資料，更新 db status
>
> 或是在寫入 cache 時把 TTL 設定比 expiredDate 更短，讓 invalidation 自動完成

### 評估
**正確的部分**：
- 第二個方案（**TTL 對齊 expiredDate**）是正確且務實的做法——讓 cache 自然過期,不需要額外機制,完全符合「不過度設計」的原則

**第一個方案需要指出問題**：
- **排程固定掃描「所有」短網址檢查 `expiredDate < now`**，本身就是一個規模不小的分散式問題：資料庫裡可能有數十億筆短網址,排程要定期全表掃描（或用 index 掃描）找出剛過期的項目,還要知道對應的 cache key 在哪個 cache 節點上才能精準 invalidate——這其實比直接依賴 TTL 自然過期複雜得多、也更耗資源,是一種可以避免的「過度設計」
- 如果兩個方案都保留，等於是「已經有 TTL 自動過期兜底，卻又額外做一個全表掃描系統做同樣的事」，這在系統設計面試中會被面試官追問「為什麼需要這個排程？TTL 不夠嗎？」

**真正需要主動 invalidation 的情境，你沒有提到**：
- 排程掃描更適合處理**「使用者手動改變 status」**的情境——例如使用者提前把某個短網址設成 `deleted`，這個改變**不在原本 TTL 的預期時程內**（TTL 是依照建立時的 expiredDate 設定的,但使用者中途刪除是計畫外的事件）。這種情況應該用 **event-driven invalidation**：在該筆資料被更新的當下，立刻精準地 invalidate 那一個 cache key，而不是等排程掃描到它

### 建議答案
> 主力做法：**寫入 cache 時，把 TTL 設成不超過 `expiredDate` 剩餘時間**，讓 cache 依照原本設計的到期時間自然失效,不需要額外系統介入——這是最簡單、成本最低的做法,能處理絕大多數「按表定時間過期」的情境。
>
> 但這個做法處理不了「計畫外」的狀態改變——例如使用者中途手動刪除短網址（`status: deleted`），這不在原本設定的 TTL 時程內。這種情況應該用 **event-driven invalidation**：當這筆資料被更新（刪除/提前過期）的當下，由該次寫入操作**直接、精準地 invalidate 那一個 cache key**，而不是另外跑一個全表掃描的排程系統去做本質上跟 TTL 重複的事。全表排程掃描的成本與複雜度（要找出哪些 key 過期、要知道 key 在哪個 cache 節點）遠高於「讓 TTL 自然到期」+「異動當下順手 invalidate」這兩個機制的組合。

## 總評

三題整體方向扎實，尤其 Q1 觀察到「建立時寫入 cache 可避免第一次讀取的 miss」是不錯的洞察。主要待加強：
1. **策略選擇時要主動點出自己選的方案有什麼代價**（Q1 的長尾分佈浪費 cache 空間問題），而不只是描述優點
2. **多處寫入的一致性/順序問題**（Q2）——這是資深工程師面試中常被追問的細節，「先寫哪裡、失敗了怎麼辦」
3. **辨識「已經有更簡單機制可以解決」時，避免疊加額外複雜系統**（Q3 的全表掃描排程 vs TTL 自然過期）——這跟 Day 2 累積的「不過度設計」弱點是同一類，值得下週持續留意
