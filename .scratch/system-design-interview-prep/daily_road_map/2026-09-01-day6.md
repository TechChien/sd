## Part 2 — Rate Limiter 概念導入（90 分鐘）

### 2.0 為什麼要 Rate Limiter（先講動機，面試開場會用到）

- **防濫用 / DoS**：單一 client 打爆後端。
- **成本控制**：下游是第三方 API（按量計費）或昂貴運算。
- **公平性**：多租戶系統，避免一個租戶吃掉所有容量。
- **與 Load Shedder 的分工**（Stripe）：
  - **Rate limiter**：以「發出請求的人」為單位做決策，是**日常、預防性**工具，client 調整頻率就能避開，結果不受影響。
  - **Load shedder**：以「整個系統當下狀態」為單位做決策，是**緊急**工具（例如 worker 使用率過高時，直接丟掉非關鍵請求）。
  - 面試講到「系統過載怎麼辦」時，要能區分這兩者——rate limiter 不是拿來救火的。

被限流時的標準回應：HTTP **429 Too Many Requests**，附 `Retry-After` header；常見再加 `X-RateLimit-Limit / -Remaining / -Reset`。

### 2.1 四種演算法

#### (a) Fixed Window Counter（固定視窗計數）
- 機制：把時間切成固定區間（如每分鐘），該區間一個計數器，超過上限就拒絕。
- 優點：實作最簡單，記憶體最省（一個 key 一個數字）。
- 致命缺點：**視窗邊界的兩倍突刺**。上限 100/min，client 在 00:00:59 打 100 個、00:01:00 再打 100 個 → 2 秒內 200 個，兩個視窗各自都「合法」。

#### (b) Sliding Window Log（滑動視窗紀錄）
- 機制：記錄每個請求的 timestamp（例如存進 Redis sorted set）。新請求進來時，先刪掉「now - window」以前的紀錄，再看剩下的數量是否 < 上限。
- 優點：**完全精確**，沒有邊界突刺問題。
- 缺點：**記憶體隨請求量線性成長**——每個請求都要存一個 timestamp。高流量下昂貴。即使請求被拒絕，通常仍會記錄（用來持續延後）。

#### (c) Sliding Window Counter（滑動視窗計數，近似）— Cloudflare 的做法
- 機制：只留「前一個固定視窗」和「當前固定視窗」兩個計數器，用加權推估當前速率：

  ```
  rate = 前一視窗計數 × (視窗剩餘比例) + 當前視窗計數
  ```

  Cloudflare 範例（上限 50/min，當前視窗已過 15 秒）：
  ```
  rate = 42 × ((60-15)/60) + 18
       = 42 × 0.75 + 18
       = 49.5   → 尚未超過 50，放行
  ```

- 假設：前一視窗的請求是**均勻分布**的（這就是近似的來源）。
- 成本：**每個 counter 只要兩個數字**，遠小於 log 法。
- 精度（Cloudflare 用 4 億次請求實測）：
  - 只有 **0.003%** 的請求被誤放行或誤限流；
  - 實際速率與推估速率**平均差 6%**。
- 額外好處：**平滑掉 fixed window 的突刺問題**。
- 這是「精確度 vs 記憶體」的實務甜蜜點，大規模系統的預設選擇。

#### (d) Token Bucket（權杖桶）— Stripe 的做法
- 機制（Stripe 原文）：有一個集中的 bucket host，**每個請求拿走一個 token**，系統以固定速率**慢慢滴入 token**；bucket 空了就拒絕請求。
- 兩個參數：`capacity`（桶容量，決定容許多大的 burst）、`refill rate`（決定長期平均速率）。
- 特性：
  - **允許可控的 burst**：桶滿時可一次消耗掉整桶，適合「平常低、偶爾尖峰」的正常流量。
  - 長期平均被 refill rate 鎖死。
- Leaky Bucket 是它的近親：請求進 queue，以**固定速率流出**——輸出完全平滑、不允許 burst。Token bucket 允許 burst、leaky bucket 不允許，這是兩者的關鍵差異。

### 2.2 選型速記

| 需求 | 選擇 |
|---|---|
| 最省事、可接受邊界突刺 | Fixed window |
| 要求絕對精確、流量不大 | Sliding window log |
| 大規模、要省記憶體又要夠準 | Sliding window counter |
| 要允許可控 burst（多數 API） | Token bucket |
| 要求輸出速率絕對平滑 | Leaky bucket |

### 2.3 Distributed Rate Limiting 的挑戰（Mock #2 的深水區，先建立問題意識）

多台 API server 共用一份限額時：

1. **狀態放哪**：本地記憶體 → 各節點各算各的，N 台 = N 倍實際限額。所以計數狀態通常集中放 **Redis**（Stripe、Cloudflare 都是）。
2. **Race condition**：`read count → check → increment` 三步非原子，兩個節點同時讀到 99、都放行 → 破限。
   解法：Redis **Lua script**（在 server 端原子執行 check+increment），或 `INCR` + 首次設定 `EXPIRE`。
3. **Redis 往返延遲 / 單點**：每個請求多一次網路往返；Redis 掛了要決定 fail-open（放行，保可用性）還是 fail-closed（拒絕，保後端）。
4. **時鐘**：多節點的視窗邊界對齊、`Retry-After` 計算都依賴一致的時間基準。

## Part 3 — Primitive 卡片（每天 mock 前唸一次）

- Redirect：`GET /{short_code}` → `301`(永久/可 cache) 或 `302`(暫時) + `Location: <long_url>`
- 限流回應：`429 Too Many Requests` + `Retry-After: <秒數>`
- 限流資訊 header：`X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`
- Sliding window counter 公式：`rate = prev_count × (1 - elapsed_fraction) + curr_count`
- Token bucket 兩參數：`capacity`（burst 上限）、`refill rate`（長期平均）
- Redis 原子計數：`INCR` + 首次 `EXPIRE`，或 Lua script
