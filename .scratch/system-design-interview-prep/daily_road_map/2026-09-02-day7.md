## Part 1 — Back-of-envelope 估算刻意練習（最高優先弱點）

> 背景：Day 3 Q2 keyspace 大小估算錯了兩個數量級以上（16 bit ≈ 65k，誤以為夠用；實際生日悖論下約 300 個就 50% 撞號）。今日把估算變成有固定流程的機械動作。

### 1.1 必背的數字錨點

| 類別 | 記住的值 |
|---|---|
| 2^10 | ≈ 1 千 (10^3) |
| 2^20 | ≈ 1 百萬 (10^6) |
| 2^30 | ≈ 10 億 (10^9) |
| 2^32 | ≈ 43 億 |
| 2^62 | ≈ 4.6 × 10^18 |
| 一天秒數 | 86,400 ≈ **10^5**（記 "10 萬秒/天"） |
| 一個月秒數 | ≈ 2.6 × 10^6 |
| 一年秒數 | ≈ 3.15 × 10^7 |
| char / short string | 1 byte（ASCII），UTF-8 中文 3 bytes |
| 一個 URL 記錄 | 約 100–500 bytes（含 metadata） |
| Base62 keyspace | 62^7 ≈ 3.5 兆；62^6 ≈ 568 億 |

### 1.2 固定四步流程（每次估算都照這個走，講出聲）

1. **寫下已知量 + 假設**：DAU、每人每日動作數、讀寫比、保留年限。假設要講出來讓面試官有機會修正。
2. **QPS**：`總日請求數 ÷ 10^5`。尖峰 QPS = 平均 × 2~10（講一個倍數並說明理由）。
3. **Storage**：`每日新增筆數 × 每筆 bytes × 保留天數`。
4. **Bandwidth**：`QPS × 每筆 payload bytes`。
5. 收尾一句：**哪個數字最大/最危險** → 那就是設計要圍繞的瓶頸。

### 1.3 練習題（先自己算，再看解答）

#### 題 A：URL Shortener（重算一次，對照 Mock #1）
已知：100M creates/day，讀寫比 100:1，保留 5 年，每筆 500 bytes。

<details>
解答：
- 寫 QPS = 100M / 10^5 = **1,000 QPS**（尖峰 ×3 ≈ 3,000）
- 讀 QPS = 1,000 × 100 = **100,000 QPS**（尖峰更高）→ **這是主瓶頸，讀路徑必須有 cache/CDN**
- 5 年總筆數 = 100M × 365 × 5 ≈ 1.8 × 10^11 ≈ **1,800 億筆**
- Storage = 1,800 億 × 500 bytes = 9 × 10^13 bytes ≈ **90 TB**
- Keyspace 檢查：需要容納 1,800 億個 code。62^6 ≈ 568 億 → **不夠**；62^7 ≈ 3.5 兆 → 夠，且佔用率 ~5%，碰撞機率可接受。所以 **short_code 至少 7 碼**。
</details>

#### 題 B：Rate Limiter 的 Redis 記憶體（連結 Day 6）
已知：1,000 萬個 active user，每個 user 對 20 個 API endpoint 各自限流。
問：(a) sliding window log (b) sliding window counter，各需多少 Redis 記憶體？

<details>
解答：
- counter 數 = 10^7 × 20 = **2 × 10^8 個 counter**
- (b) sliding window counter：每 counter 2 個整數，約 16 bytes + Redis key 開銷 ~64 bytes ≈ 80 bytes → 2×10^8 × 80 = 1.6 × 10^10 ≈ **16 GB**。單台大記憶體 Redis 可撐，或分片。
- (a) sliding window log：每 counter 存 N 個 timestamp（N = 限額，假設 100），每個 timestamp 8 bytes → 每 counter ~800 bytes + 開銷 → 約 900 bytes → 2×10^8 × 900 ≈ **180 GB**。差一個數量級，必須分片。
- 收尾：這就是 Day 6 說的「精確度 vs 記憶體」取捨的具體數字。
</details>

#### 題 C：生日悖論快速判斷（Day 3 Q2 的直接補強）
規則：在 keyspace 大小 K 中隨機取值，約取 **√K** 個就有 ~50% 機率出現碰撞。
- 16 bit：K = 65,536 → √K ≈ **256** → 取幾百個就撞。（Day 3 的錯誤在此）
- 62^7 ≈ 3.5×10^12 → √K ≈ **1.9 × 10^6** → 約 200 萬個才 50% 撞——但我們要放 1,800 億個，遠超過 √K，**所以純 random 一定會頻繁碰撞，必須查 DB 檢查 + 重試**，或改用 KGS / Snowflake（結構性保證唯一）。
- **面試話術**：講到隨機產生 ID/code 時，主動說一句「by birthday paradox, collisions start around √(keyspace), so with K codes to store I need keyspace ≫ K² to make collisions negligible without a check」。

## Part 2 — Week 1 Building Blocks Cheat Sheet

### Day 1：Scalability / Availability / Consistency / CAP
- **CAP**：網路分區（P）發生時，只能二選一：
  - **CP**：拒絕部分請求以保一致（如需要強一致的金流、庫存）
  - **AP**：仍回應但可能回舊資料（如社群 feed、DNS）
  - 無分區時不需要犧牲——CAP 只在 partition 當下逼你選。
- **一致性模型**：strong / eventual / causal。URL Shortener 的 redirect 可接受 eventual（新建短碼晚幾秒生效 OK）。
- **可用性**：99.9% = 每年停 ~8.7 小時；99.99% = ~52 分鐘。串接的服務可用性相乘。
- 來源：[system-design-primer — CAP / Consistency / Availability patterns](https://github.com/donnemartin/system-design-primer#consistency-patterns)

### Day 2：Load Balancing / DNS / Application layer
- **DNS**：網域 → IP，可做地理導流、round-robin。TTL 決定快取時間。
- **L4 LB**：看 TCP/UDP header（IP+port）轉發，快、不看內容。
- **L7 LB**：看 HTTP 內容（path、header、cookie），可做 path-based routing、sticky session，成本較高。
  - Mock #1 弱點：要能講「L7 讓我可以把 `/api/*` 和 redirect 熱路徑分流到不同 pool」這種**具體機制**，不只說「LB 分散流量」。
- **LB 演算法**：round-robin / least connections / IP hash。
- **水平擴展先於垂直**：無狀態 app server 放 LB 後面，session 外置（Redis）。
- 來源：[system-design-primer — Load balancer / Reverse proxy](https://github.com/donnemartin/system-design-primer#load-balancer)

### Day 3：SQL vs NoSQL / Sharding / Replication / Federation
- **KV store 適配性**：`key → value` 單鍵查詢、無 join → 教科書級 NoSQL/KV 場景（Day 3 Q1 弱點：要先點出這一面，再說明為何仍可選 SQL+cache）。
- **選型務實原則**：先用熟悉、低複雜度的 SQL+cache，除非量體真的把 SQL scaling 壓垮才引入 NoSQL。
- **Federation**：把單一 DB **依功能領域拆**（users DB / products DB / forums DB）。不是「整合異質資料」（Day 3 Q3 記反了）。適用「多功能領域、各自量還不到要 shard」。
- **Sharding**：同一 entity 依 key 水平切。shard key 選「幾乎所有查詢都會帶的欄位」（URL shortener → `short_code`），避免 scatter-gather。
- **`hash mod N` 陷阱**：N 改變 → 幾乎全部 key 重新映射 → 用 **consistent hashing**（增減節點只影響一小段 key，Week 2 Day 3 深入）。
- **Replication**：master-slave（讀擴展、slave 可提升為 master）vs master-master（寫擴展、衝突處理複雜）。replication lag → 讀到舊資料。
- 來源：[system-design-primer — Database](https://github.com/donnemartin/system-design-primer#database)

### Day 4：Caching
- **Cache-aside（lazy load）**：app 先查 cache，miss 就查 DB 再寫回 cache。最常見。缺點：miss 時多一次往返；資料可能過期。
- **Write-through**：寫入時同時寫 cache + DB。讀永遠命中新資料，寫變慢。
- **Write-behind**：寫 cache 後非同步刷 DB。寫最快，但 cache 掛了會掉資料。
- **多層 cache**：本地 LRU → Redis → DB（Mock #1 你答對這層架構）。
- **Dual-write 順序問題**（Day 4 Q2 弱點）：同時寫 DB 和 cache 時，要先想清楚**寫入順序**與**其中一步失敗怎麼辦**。常見安全做法：先寫 DB，成功後**刪除**（非更新）cache，讓下次讀觸發 cache-aside 重新載入。
- **TTL 自然過期 vs 全表掃描排程**（Day 4 Q3 弱點）：能用 TTL 讓資料自然過期，就不要另外寫排程掃全表——不過度設計。
- **CDN**：靜態內容 / redirect 結果推到邊緣節點。`301` 可被 CDN/瀏覽器快取，`302` 通常不快取。
- 來源：[system-design-primer — Cache](https://github.com/donnemartin/system-design-primer#cache)
