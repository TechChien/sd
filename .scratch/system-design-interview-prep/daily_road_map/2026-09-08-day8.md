## Part 2 — Distributed Rate Limiting 完整設計（核心，90 分鐘）

### 2.1 問題重述

單機 rate limiter 很簡單（記憶體裡一個 counter）。一旦有 N 台 API server 分攤流量，兩條路：

- **A. 狀態集中**（Redis/memcached 等）：所有節點打同一份計數 → 準，但多一次網路往返、有單點風險。
- **B. 狀態各自局部**：每節點自己算 → 快、無單點，但 N 節點各自的限額視窗會讓總量最多超出到 N 倍實際限額。

這是本題的核心 trade-off：**準確度 vs 延遲/可用性**，跟 CAP 是同一種形狀的取捨（Day 1 教過的框架可以直接套用）。

### 2.2 方案 A：集中式狀態（Stripe 的做法）

來源：[Scaling your API with rate limiters — Stripe blog](https://stripe.com/blog/rate-limiters)

- Stripe 用 **Redis**（自架或 AWS ElastiCache）當集中 bucket host，token bucket 演算法，每個 user 一份 bucket 狀態。
- **Race condition**：`read → check → decrement/increment` 若不是原子操作，兩台 API server 同時讀到「還有 1 個 token」，都放行 → 破限。
- 解法（Day 6 已提過，今天釘死機制）：
  - **Redis Lua script**：把 read-check-write 包成一支腳本，Redis 單執行緒保證整支腳本原子執行，等同做了一次 server 端的 compare-and-swap。
  - 或簡化版：`INCR` 是原子操作，配合首次 `EXPIRE` 設定視窗 TTL，適合 fixed window / sliding window counter 這種「只需要一個遞增數字」的演算法；token bucket 因為要同時算「取多少 token + 何時 refill」，通常還是需要 Lua script 而非單純 INCR。
- **Fail-open 設計原則（Stripe 明講的核心哲學）**：
  > "If there were bugs in the rate limiting code (or if Redis were to go down), requests wouldn't be affected."
  - 所有例外都要 catch，rate limiter 掛了 → **放行**而不是全部拒絕。
  - 理由：rate limiter 是預防性工具（Day 6 區分過的 rate limiter vs load shedder），它本身故障不該變成一次自我 DoS。
  - **面試加分句**：主動說「我會讓 rate limiter fail-open，因為它的故障模式不該比它要防的問題更糟」。
- **上線安全機制**（Stripe 實務，面試官問「怎麼上線」時可以用）：
  - Kill switch / feature flag：出問題能立刻關掉。
  - **Dark launch**：先只記錄「這個規則會擋掉哪些流量」不真的擋，觀察後再啟用，避免誤傷正常流量。
  - 監控每個限流規則觸發次數，異常要能告警。
- Stripe 的**四層架構**（面試官問「系統過載時全套怎麼做」可以用這個當骨架，同時複習 Day 6 rate limiter vs load shedder 的分工）：
  1. Request rate limiter — 每 user 每秒 N 次，最常觸發，允許短暫 burst。
  2. Concurrent requests limiter — 限制同一 user 同時in-flight 的請求數（如上限 20），防止重試風暴造成資源爭用。
  3. Fleet usage load shedder — 保留一部分容量給關鍵請求（如 charge creation），非關鍵請求超額直接 503。
  4. Worker utilization load shedder — 最後防線，系統嚴重過載時分級丟棄（critical methods > POST > GET > test mode），漸進丟棄避免震盪（flapping）。
  - 1、2 是 rate limiter（以 client 為單位、日常），3、4 是 load shedder（以系統整體狀態為單位、緊急）。

### 2.3 方案 B：Anycast + 局部狀態（Cloudflare 的做法）

來源：[Counting things: A lot of different, distributed, things — Cloudflare blog](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)

Cloudflare 面對的量級（每網域可能到 40 萬 QPS 的攻擊流量）讓「每個請求都問一次集中式 Redis」不可行，所以走了跟 Stripe 完全不同的架構：

- **靠 anycast 網路特性**：同一個來源 IP 在正常情況下會固定打到同一個 PoP（資料中心），所以**不需要跨 PoP 同步計數**，每個 PoP 內部自己算自己的就夠準。
- **PoP 內部**：用 Twemproxy 把計數分散到多台 memcached，靠 consistent hashing 決定 key 落在哪台（呼應 Day 3 的 consistent hashing 概念，這裡是它的一個實際應用場景）。
- **演算法選型也是為了降低協調成本**：
  - Leaky bucket 更精確，但需要多次原子 memcached 操作 → 攻擊流量下造成大量鎖競爭（contention）。
  - Fixed window 最簡單，但邊界突刺問題（Day 6 教過）。
  - 最終選 **sliding window counter**：只需要 `GET` + `INCR` 兩個操作，協調成本最低，同時解決突刺問題。
- **非同步化進一步降低延遲影響**：counter 遞增是非同步做的（不擋請求路徑），且一旦某來源被判定要限流，決策會被**本地快取**，同一 client 後續請求不用再查 memcached。
- **這一段的面試話術**：跟 Stripe 對比著講——「如果流量集中在少數幾個地理區域且延遲敏感，可以考慮 anycast + 局部計數，犧牲跨區絕對精確換取低延遲；如果是像 Stripe 那樣單一 region、per-user 計費相關的限流，準確度優先，走集中式 Redis + fail-open」。這正是 Day 7 checklist 第 6 點（選策略要講代價）的具體練習。

### 2.4 其他共通的 distributed 難點（Day 6 提過問題意識，今天釘死解法）

1. **Redis 單點/延遲**：
   - 單點風險：Redis 本身可以做 replication（Day 3 教過的 master-slave），或分片降低單台負載。
   - 延遲：每請求多一次網路往返，可用非同步遞增（Cloudflare 的做法）或本地快取「已知超限」的決策降低查詢次數。
2. **時鐘同步**：多節點視窗邊界對齊、`Retry-After` 計算依賴一致時間基準；用 Redis 自己的時間（`TIME` 指令）而非各節點本地時鐘，避免 clock skew（跟 Week 7 的 Snowflake clock skew 問題同一類）。
3. **fail-open vs fail-closed 的選擇本身也是一個要主動講代價的決策**：
   - fail-open（Stripe 選這個）：可用性優先，代價是故障時失去限流保護。
   - fail-closed：安全優先（如金流類 API 可能選這個），代價是 Redis 掛了會直接擋掉所有流量，故障半徑被放大。

## Part 3 — 練習題（先自己口說作答，再對照要點）

### 題 1
「你的 API 服務部署在 3 台無狀態 app server 後面，要做『每 user 100 req/min』的限流。請設計，並說明如果 Redis 掛了你怎麼辦。」

<details>
要點：
- 狀態集中在 Redis（跨 3 台共用同一份計數，否則各自算會變成最多 300 req/min）。
- 演算法選 sliding window counter（大規模、省記憶體、無突刺）或 token bucket（若要允許 burst）。
- 原子性：Lua script 或 INCR+EXPIRE。
- Redis 掛了 → fail-open，並說明理由（rate limiter 故障不該讓核心功能整個不可用）。
- 加分：提 kill switch / dark launch / 監控。
</details>

### 題 2
「你的服務是全球 CDN 等級流量（想像類似 Cloudflare 的場景），单一集中式 Redis 會不會有問題？」

<details>
要點：
- 集中式 Redis 在超大流量、多地理區域下延遲/單點風險放大。
- 若流量有地理局部性（anycast 或類似的路由保證同一來源固定到同一節點），可以改成局部計數，不需要跨節點同步。
- 主動點出這是「準確度 vs 協調成本」的取捨，並給出量化：sliding window counter 在 Cloudflare 實測誤差約 6%，換來大幅降低協調成本。
</details>

### 題 3（compound，刻意練習 Day 6/7 的 paraphrase 弱點）
「如果我們要求限流『絕對不能』因為 Redis 故障而被繞過，這時候你選 fail-open 還是 fail-closed？那如果同時要求可用性 99.99%，這兩個要求會不會衝突，你怎麼決定？」

<details>
練習重點：這題有兩個子問題（fail-open/closed 的選擇；兩個需求是否衝突），作答前先覆述：
「So first you're asking which one I'd pick given the 'never bypass' requirement, and then whether that conflicts with the 99.99% availability target — right?」
再回答：
- 「絕對不能被繞過」本質上要求 fail-closed（限流器是安全邊界的一部分，故障時應該擋而非放行）。
- 這確實跟高可用性目標衝突——fail-closed 意味著 Redis 故障會讓所有流量被擋，直接打穿可用性目標。
- 解法方向：不是非黑即白選一個，而是降低 Redis 本身故障率（replication + failover）、把 fail-closed 的影響範圍縮小到真正需要「絕對不能繞過」的高風險端點（如金流），其餘端點仍 fail-open。這也是 Day 7 checklist「不過度設計」+「講代價與緩解」的綜合練習。
</details>
