## Part 1 — Mock #2 Debrief：把 findings 變成「下次可執行的動作」（30 分鐘）

### 1.1 選型必帶代價（checklist #6，Mock #2 被追問 ≥3 次）

**觸發條件**：你講出「我選 X」這三個字的當下。
**固定句型（同一口氣講完，不等追問）**：

> "I'd go with **X**. The cost is **___**, and I'd mitigate it with **___**."

Mock #2 的三個現場例子，先各講一次：
- capacity = 20：cost = 閒置 key 可瞬間打出 20 個請求的 burst 打到後端；mitigate = capacity 綁到後端可承受的瞬時併發（從 concurrent limit 反推），不是憑感覺選。
- one global Redis：cost = 每次 API call 一次跨洋同步往返 +100~150ms；mitigate = 改 per-region Redis，接受 per-region 計數的近似。
- payments fail-open：cost = Redis 掛掉時無上限的請求洪水打進 payment 後端，反而擴大故障半徑；mitigate = 降級成 gateway 本地的粗略 fallback limiter（不是 cache）。

### 1.2 Compound 問題先覆述（checklist #1，Mock #1 頭號 carry-over，Mock #2 仍未做且答反）

**觸發條件**：問題裡有「and」「then」「does it interact with」「if it's X instead」，或問題引用你前面講過的東西。
**固定動作**：回答前先講一句：

> "Let me make sure I've got both parts: you're asking **(a) ___**, and **(b) ___** — right?"

覆述完**先停半秒等對方點頭**，再回答。這半秒是重點——它強迫你把兩個子問題都放進工作記憶，Mock #2 答反 fail-open/fail-closed 就是因為只抓到「payments」這個詞就衝出去答。

**fail-open / fail-closed 釘死（Mock #2 答反且堅持不改）**：
- **fail-open** = 元件故障時**放行**。可用性優先。一般 web API 用這個（Stripe 官方就是這個選擇）。
- **fail-closed** = 元件故障時**拒絕**。安全/正確性優先。金流、認證、付費牆這種「放行的代價 > 拒絕的代價」的場景用這個，或至少加強本地 fallback。
- 助記：**open = 門開著 = 讓你過**；**closed = 門關著 = 擋你**。

### 1.3 拿到數字就要用（checklist #3，Mock #2 給了 4 個數字一個都沒用）

**觸發條件**：面試官說出任何數字（keys、QPS、active users、limit）。
**固定動作**：當場口頭算三件事的其中相關者，寫在白板角落：
1. **狀態記憶體**：active key 數 × 每 key bytes。Mock #2：200k active keys × (2 個 int ≈ 16B + key overhead ≈ 64B) ≈ 200k × 80B ≈ **16 MB per region**。→ 結論一句：「單台 Redis 記憶體完全不是問題」。
2. **單節點吞吐**：per-region 請求率 vs 單 Redis 上限。500k req/s ÷ 3 region ≈ 167k req/s；單執行緒 Redis 約 100k~200k ops/s → **接近上限，需要分片或 pipeline**。這個結論直接引出今天的 consistent hashing。
3. **從 limit 反推參數**：1,000 req/min → refill_rate = 1000/60 ≈ **16.7 tokens/s**（要把 1000/60 講出來，不要只報結果）。

### 1.4 不確定就明說（Mock #2 硬套 CAS）

**觸發條件**：你心裡在翻「有沒有哪個術語聽起來對」。
**固定句型**：

> "I'm not immediately sure how to bound that — let me reason through it out loud."

然後從第一性原理推。Mock #2「怎麼把跨 region 3x overshoot 壓下來」的正解方向（不是 CAS）：
- 每個 region 分到 global limit 的一份配額（例：各 333/min）。
- 背景程序週期性（如每 10s）彙總三個 region 的實際用量，**動態調整配額**給流量大的 region 多分一點。
- worst case：在彙總週期內，某 key 流量突然全湧向一個 region，該 region 最多放行 (它的配額 + 一個週期的偏移)，永遠不會到 3x。
- 代價（記得帶！）：配額同步有延遲，短時間內仍可能小幅超發；mitigate = 縮短彙總週期 or 對高風險 key 收緊配額。

## Part 2 — Consistent Hashing（核心，90 分鐘）

### 2.1 為什麼需要它：naive `hash(key) mod N` 的致命傷

你有 N 台節點（cache server / DB shard / rate-limiter counter shard），要決定 key 放哪台。最直覺：

```
node_index = hash(key) mod N
```

**問題**：N 一變（加一台、掛一台），`mod N` 對幾乎**每一個 key** 都算出不同的結果。

- 來源（Toptal）：三台變兩台時，「all key locations changed, not only the ones from server C」。
- 對 cache 的後果：幾乎全部 key 同時 miss → 請求全部穿透到後端 DB → DB 被打垮（cache stampede 的放大版）。
- 對 DB shard 的後果：加一台機器要搬移近 100% 的資料。

**這就是 Mock #2 的 per-region Redis 想分片時會撞到的牆**，也是 Week 2 Day 4 Distributed Cache 的核心。

### 2.2 Hash Ring 怎麼運作

把 hash 的輸出空間想成一個**環**（0 到 2^32-1 首尾相接）。

1. **放節點**：對每個節點的識別字（如 IP、名字）做 hash，落在環上某個點。
2. **放 key**：對 key 做 hash，落在環上某個點。
3. **歸屬規則**：從 key 的位置**沿順時針**走，遇到的第一個節點就是負責的節點。（順/逆時針只是慣例，一致即可 —— Toptal 用逆時針，多數實作用順時針。）

實作上：把所有節點位置存成一個**排序陣列**，key 查詢就是一次 **binary search**（找第一個 ≥ key 位置的節點，繞回開頭處理 wrap-around）。這是它相對 `mod N` 多出的成本：要維護排序結構 + O(log N) 查詢。

### 2.3 關鍵性質：加/減節點只影響 K/N 個 key

- **公式（Toptal）**：只有 **k/N** 個 key 需要重新映射，k = 總 key 數，N = 變動前後節點數的較大值。
- 移除一台（3→2）：只有原本屬於那台的 ~1/3 key 需要搬到它順時針方向的下一台，**其他 2/3 完全不動**。
- 加一台（3→4）：新節點插入環上某點，只從它順時針方向的**下一台**手上「接走」一段區間的 key，其餘節點不受影響。
- 對比 `mod N` 的近 100% 搬移，這是數量級的差距。

**面試話術**：「用 consistent hashing 而不是 hash mod N，因為擴縮容時只有約 1/N 的 key 需要重新分配，其餘不動；代價是要多維護一個排序的環結構跟 O(log N) 查詢，而且**基本版負載不均**——這就要靠 virtual node 解決。」（選型 + 代價 + 緩解，一口氣講完，就是 Part 1.1 的模式。）

### 2.4 Virtual Nodes（vnodes / replicas）：解決負載不均與異質機器

**基本版的問題**：只有 3 個節點點位在環上，環被切成 3 段的大小隨機，可能一台管 50%、一台管 20%。移除一台時，它的負載也全部壓到單一鄰居而非均攤。

**解法**：每個實體節點在環上放 **V 個點位**（A0..A9, B0..B9, C0..C9），用 `hash(node_id + i)` 產生。

- **均勻性**：點位越多，每台管的總弧長越接近 1/N。Toptal：3 台用 weight 10 就夠；大叢集要 100~500。
- **比例分配（異質機器）**：給效能兩倍的機器兩倍的 vnode 數 → 它平均分到兩倍資料。直接回答 Mock #2 沒答好的「怎麼讓不同容量的節點分不同流量」。
- **故障時均攤**：一台掛掉，它的 V 個點位各自把負載交給環上不同的鄰居 → 負載打散到多台而非壓垮一台。

**代價**：vnode 越多，環結構越大、查詢常數變大、rebalance 時要移動的 metadata 變多。實務取一個夠用的中間值。

### 2.5 固定分區（fixed partitions）變體

paperplanes.de / Dynamo 風格：不讓節點在環上選隨機點，而是**預先把環切成 Q 個固定大小的分區**（Q 遠大於節點數），節點認領分區。

- 「everyone gets an equally large slice」——分區大小固定可預測。
- 加節點 = 從現有節點手上轉移**整數個分區**，不需要動 key-level 的 hash。
- Replication 直接掛在分區上：「every node is simply a replica of a number of partitions」。
- 採用者：Amazon Dynamo、Cassandra、Riak。

### 2.6 真實系統

- **memcached client 端**（ketama）、**Amazon Dynamo**、**Cassandra**、**Riak** 都用 consistent hashing 做資料分佈。
- **Cloudflare 的 rate limiter**（Day 8 Part 2.3）：PoP 內部用 Twemproxy + consistent hashing 把計數 key 分散到多台 memcached —— 這就是 consistent hashing 在**基礎設施型**題目裡的實際落點，不只出現在 Distributed Cache。
- 侷限：基本版負載不均（→ vnodes）；環 metadata 需要在所有節點間有一致視圖（gossip 或 coordinator）；熱點 key 單靠 consistent hashing 解不了（那是 replication / request coalescing 的範疇，Day 4 會碰）。

### 2.7 一句話總結（面試可背）

> Consistent hashing 把節點和 key 都映射到同一個 hash 環，key 歸給順時針第一個節點；好處是加減節點只搬約 1/N 的 key，代價是要維護排序環 + 基本版負載不均，用 virtual nodes（每節點多個環上點位）解決均勻性並順便支援異質機器的比例分配。

## Part 3 — 練習題（先口說作答，再對照）

### 題 1（機制，非術語）
「你有 4 台 cache node 用 `hash(key) mod 4` 分流。現在要加到 5 台。會發生什麼？consistent hashing 怎麼改善，改善多少？」

<details>
- mod 4 → mod 5：4/5 的 key 算出不同 index → 近 80% cache miss 同時發生 → 後端被打穿。
- consistent hashing：新節點插入環，只從順時針下一個節點接走約 1/5 的 key，其餘 4/5 不動。
- 量化：K/N ≈ K/5，約 20% vs 80%。
- 代價一句：多維護排序環 + O(log N) 查詢；基本版負載不均要 vnode。
</details>

### 題 2（連到 Mock #2）
「Mock #2 你把 rate-limiter 計數放 per-region Redis，單台 region 要吃約 167k req/s 逼近單 Redis 上限。你要分片。用什麼分、加機器時怎麼辦？」

<details>
- 分片 key = API key（同一 client 的計數要落同一片才能正確計數）。
- 用 consistent hashing 決定 API key → shard，不用 mod N。
- 加機器：只有約 1/N 的 API key 的計數要搬；搬移期間該批 key 可短暫 fail-open 或雙寫舊新片。
- 代價：跨片無法做全域彙總 → 若需要「全 region 總量」仍要背景 aggregation（Part 1.4）。
- 帶數字：167k req/s ÷ 每片 ~100k ops/s → 至少 2 片，留 headroom 取 3~4 片。
</details>

### 題 3（compound，刻意練 paraphrase）
「如果其中一台 shard 掛了，(a) 用基本版 consistent hashing 跟用 virtual nodes，這台的負載各自會怎麼轉移；(b) 如果這是 rate-limiter 的計數 shard，掛掉的瞬間對『限流準確度』有什麼影響，你會 fail-open 還是 fail-closed？」

<details>
先覆述：「兩部分：(a) 掛一台時 basic vs vnode 的負載轉移差異，(b) 這是計數 shard 時對準確度的影響 + fail-open/closed 選擇 —— 對嗎？」
- (a) basic：整段弧全部壓到順時針單一鄰居，該鄰居負載可能翻倍。vnode：掛掉節點的 V 個點位各自交給不同鄰居，負載打散到多台，每台只多 ~1/(N-1)。
- (b) 該 shard 上的 API key 暫時沒有計數狀態 → 重建前這些 key 的限流視窗歸零（可能放行超量）。一般 API：fail-open（限流器故障不該變成自我 DoS，Stripe 哲學）。金流類端點：對這批 key 降級成 gateway 本地粗略 fallback limiter（近似 fail-closed 的效果但不整個擋死）。
- 代價：fail-open 期間該批 key 可超發；mitigate = shard 加 replica 縮短重建時間 + 高風險端點本地 fallback。
</details>
