## Part 1 — Cache Eviction Policy（40 分鐘）

### 1.1 為什麼需要 eviction：RAM 有限

Primer：cache 常見用法是「in-memory caches such as Memcached and Redis」，靠「cache invalidation algorithms such as least recently used (LRU)」把「cold」entry 踢掉、把「hot」data 留在 RAM——因為 RAM 比 disk 貴且小得多。

Primer 對 eviction 的機制本身講得很淺，只提到 LRU 這個名字。今天用 **Redis 官方文件**把機制講清楚，這也是 Mock #3（Distributed Cache）最可能被追問「eviction 怎麼選、怎麼實作」的地方。

### 1.2 觸發條件：`maxmemory`

Redis 用 `maxmemory` 設定 cache 可用記憶體上限。**關鍵**：當有 replication 或 persistence 時，master 要用一塊記憶體當 buffer 存「還沒送到 replica / AOF 的更新」，這塊 buffer **不算進** `maxmemory` 比較的用量——因為 eviction 本身也會產生要送到 buffer 的更新（DEL command），如果算進去會造成 feedback loop，越 evict 越觸發更多 evict。

**面試延伸**：這代表**有 replica 的 Redis 要把 `maxmemory` 設得比實體記憶體小一截**，留空間給這個 buffer，否則會在還沒到 `maxmemory` 前就先 OOM。

### 1.3 六種（+ 新增兩種）policy，對應「你在乎什麼」

| Policy | 對象 | 淘汰依據 |
|---|---|---|
| `noeviction` | 全部 key | 不淘汰，寫入直接報錯（讀照常） |
| `allkeys-lru` | 全部 key | 最久沒被存取（approximate LRU） |
| `allkeys-lfu` | 全部 key | 存取頻率最低（approximate LFU） |
| `allkeys-lrm`（Redis 8.6+） | 全部 key | 最久沒被**修改**（只看 write，不看 read） |
| `allkeys-random` | 全部 key | 隨機 |
| `volatile-lru`/`lfu`/`lrm`/`random` | 只有設 TTL 的 key | 同上邏輯，範圍縮小到有 TTL 的 key |
| `volatile-ttl` | 只有設 TTL 的 key | 剩餘 TTL 最短的先踢 |

**選型口訣（Redis 官方建議 + Part 1.1 選型句型套用）**：
- 預設優先選 **`allkeys-lru`**：因為大多數存取符合 **Pareto principle**（少數 key 占大多數存取），LRU 能準確抓住這種「熱點集中」pattern。
- 存取頻率大致均勻（如循環讀取）→ `allkeys-random`，因為 LRU/LFU 的排序成本在這種情境下拿不到好處。
- 應用層自己能判斷「這個 key 之後不會再被讀」→ 主動設短 TTL，用 `volatile-ttl`，還能讓 key 自然過期、根本不必走到 eviction（呼應 spec 弱點清單「全表掃描排程 vs TTL 自然過期」那組判斷力）。
- 想同時放「純 cache 用的 key」跟「不能丟的持久 key」在同一個 Redis → 官方**不建議**（用 `volatile-xxx`），建議直接拆成兩個獨立 Redis instance。
- **新增 `allkeys-lrm`**：只在乎「有沒有被寫過」而不管「有沒有被讀過」時用——適合區分「熱資料但唯讀」vs「已經沒人更新的資料」，跟 LRU 的差異是判準只看 write 不看 read。
- 代價一句（Part 1.1 句型）：選 `allkeys-lru`，代價是要多一份 access-order 追蹤結構且對「均勻存取」場景沒有比 random 更好；緩解 = 用 `INFO stats` 的 `keyspace_hits/misses` 跟 `evicted_keys` 驗證假設是否成立，不是靠感覺選。

### 1.4 LRU 和 LFU 都是「近似」，不是精確計算

**這是最容易被追問到的細節**：Redis **不做真正的 LRU**，因為精確追蹤「每個 key 的存取順序」成本太高（要維護一個全域有序結構）。改用**近似演算法**：

- **Approximated LRU**：每次要淘汰時，**隨機抽樣**一小批 key（預設 `maxmemory-samples 5`），從樣本裡挑「最久沒被存取」的踢掉。Redis 3.0 起額外維護一個「候選淘汰池」，讓近似值更接近真實 LRU。樣本數可調（`CONFIG SET maxmemory-samples 10`），樣本越大越接近真 LRU，代價是多耗 CPU。
- **Approximated LFU**：一樣用抽樣，但排序依據換成**存取頻率**，用一個叫 **Morris counter**（機率計數器，只需幾個 bit）估計頻率，並搭配 **decay**：預設每分鐘讓計數器衰減一次、約 100 萬次存取讓計數器飽和（`lfu-decay-time`、`lfu-log-factor` 可調）。decay 存在的理由：不然「很久以前紅過的 key」會一直被誤判成熱點，LFU 就失去「跟上存取模式變化」的能力。

**面試話術（選型+代價+緩解，Part 1.1 句型）**：「Redis 的 LRU/LFU 都是近似算法而非精確排序，代價是淘汰結果跟理論最優會有機率性偏差；緩解是提高 `maxmemory-samples`，Redis 官方測試顯示樣本數 10 已經非常接近理論 LRU 表現，尤其在存取符合 power-law 分布時差距幾乎消失。」

### 1.5 練習題 1（口說作答）

「你的 cache 存的是『使用者最近 7 天的 session』，讀寫都很頻繁，但過期後就該完全消失、不該占記憶體。你選哪個 eviction policy？為什麼不選 `allkeys-lru`？」

<details>
- 選 `volatile-ttl`（或搭配主動設定 7 天 TTL，讓 key 大多在到 `maxmemory` 前就自然過期，不需要真的走 eviction）。
- 不選 `allkeys-lru`：LRU 是「猜」哪個 key 未來不會再被存取，但這裡我們**已經確定知道**「7 天後一定不需要」，不需要用猜的，直接用 TTL 表達精確資訊比較準。
- 代價：如果應用層設錯 TTL（設太短），資料會提前消失且無法挽回；緩解 = 監控 `expired_keys` 是否符合預期速率。
</details>

## Part 2 — Cache Replication（40 分鐘）

### 2.1 跟 Day 3 的 DB master-slave 是同一套模式

Primer 對 DB replication 的描述：「The master serves reads and writes, replicating writes to one or more slaves, which serve only reads.」缺點是「Additional logic is needed to promote a slave to a master」，以及一般性缺點——master 掛掉前還沒同步完的資料會丟、read replica 太多會拖慢 replication、replication lag。

**Redis 官方文件把同一套模式套用在 cache 上**，用詞是 leader-follower（master-replica），機制細節比 primer 深很多，今天補這塊。

### 2.2 Redis replication 機制：三段式

1. **正常連線**：master 把「造成資料變化的動作」（client 寫入、key 過期、key 被 evict）持續以 command stream 推給 replica。
2. **斷線重連**：replica 用 `PSYNC` 帶著「舊 replication ID + 已處理到的 offset」跟 master 要求**部分重同步（partial resync）**——只補斷線期間漏掉的那一段 command。
3. **無法部分同步時**（backlog 不夠、或 replication ID 對不上）：**完全重同步（full resync）**——master 產生一份 RDB 快照、傳給 replica、replica 載入後再接上後續 command stream。

### 2.3 Async by default：跟你以為的不一樣

**這題面試很愛問，容易答錯**：Redis **預設是非同步複製**——master 執行寫入後**不等** replica 確認就回應 client。Replica 只是「定期非同步回報」自己處理到哪個 offset，master 藉此知道每個 replica 的進度，但**不會因此卡住寫入**。

**代價**：master 掛掉時，「已經回應給 client 成功、但還沒傳到任何 replica」的寫入會直接丟失。

**緩解（但不是解決）**：`WAIT` 指令可以讓 client 主動要求「等到 N 個 replica 確認收到這筆寫入」才算完成，把資料丟失的機率壓低。但官方原文講得很直白：「it does not turn a set of Redis instances into a CP system with strong consistency: acknowledged writes can still be lost during a failover」——`WAIT` 只是**降低機率**，不是**保證**。這正好對應 spec 弱點清單「容易混淆『機率極低』與『保證』的差異」，這裡是同一類陷阱的另一個現場：不要把「用了 WAIT」講成「資料不會丟」。

### 2.4 Replica 預設唯讀，且不建議改

Redis 2.6 起 replica 預設 **read-only**（`replica-read-only yes`），拒絕所有寫入指令。雖然可以改成 writable replica，但官方**不建議**：因為 replica 的資料一旦跟 master 產生分歧（例如 master 上某 key 已過期、has 不同 type），master 傳來的 `DEL`/`INCR` 之類命令在 replica 上套用時可能失敗或產生不同結果，導致 master 跟 replica **不一致**，而且「這種寫入一旦 resync 就會被沖掉，且不保證會自動 resync」。

**面試話術**：「cache 的 read replica 用來做讀取的水平擴充跟提高可用性，但不該拿來接寫入——這跟 DB master-slave 是同一個道理：寫入路徑要單一權威來源，否則會有分歧與衝突解決的問題。」

### 2.5 誰負責 eviction？→ 只有 master

**這是 Part 1（eviction）跟 Part 2（replication）真正的交會點**，也是最容易被追問到的組合題：

> Replica **預設完全不自己做 eviction**（忽略自己的 `maxmemory` 設定）。當 master 因為 `maxmemory` 觸發 eviction，踢掉一個 key 時，master 會把這個動作**合成一個 `DEL` 命令**傳給所有 replica，replica 執行這個 `DEL` 來跟 master 保持一致——**不是自己獨立跑一份 eviction 演算法**。

**為什麼要這樣設計**：如果 master 跟每個 replica 各自獨立跑近似 LRU/LFU（有隨機抽樣），淘汰的 key 極可能不一樣——master 跟 replica 的資料集就會分歧。用「master 決定、廣播 DEL」保證所有節點淘汰的是**同一組 key**。

**代價**：replica 因此可能暫時比 `maxmemory` 用更多記憶體（自己的 buffer、資料結構開銷都不受限），需要另外監控、給 replica 留足夠 headroom，而不能只靠 `maxmemory` 卡死。

**同理，TTL 過期也是 master 驅動**：replica 不會自己主動把過期 key 刪掉，而是等 master 送 `DEL`（因為 master/replica 之間無法假設時鐘同步）。但 replica 在**純讀取**且不違反一致性的前提下，會用自己的邏輯時鐘判斷「這個 key 邏輯上已經過期了」而回報不存在，避免回傳一個其實已經該消失的值。

### 2.6 練習題 2（compound，練 paraphrase，連到 Day 9 consistent hashing）

「你的 Distributed Cache 用 consistent hashing 把 key 分到 5 個 shard，每個 shard 是一組 master + 2 個 replica。(a) 如果只看『資料一致性』，replica 落後 master 會造成什麼問題；(b) 如果一個 shard 的 master 掛了、promote 一個 replica 頂上，eviction 的行為會發生什麼變化？」

<details>
先覆述：「兩部分：(a) replica 落後對讀取一致性的影響，(b) master 掛掉、replica 被 promote 後 eviction 行為的變化——對嗎？」

- (a) Redis 是 async replication，replica 的資料是**最終一致（eventually consistent）**、有 replication lag。如果讀取被路由到 replica（例如讀寫分離減輕 master 負擔），可能讀到比 master 舊的值，甚至讀到「master 已經因為 eviction 或過期刪除、但 DEL 還沒送達」的過時資料。代價：讀到 stale data；緩解 = 對「必須讀到最新值」的請求強制路由到 master，其他容忍 staleness 的請求才讀 replica。
- (b) Promote 前，這個 replica 完全不做 eviction、忽略自己的 `maxmemory`（等 master 的 `DEL`）。**Promote 之後**，它變成新 master，會**開始自己獨立跑 eviction 演算法**（近似 LRU/LFU），不再等別人。如果 promote 前它因為「忽略 maxmemory」已經超出設定值，promote 那一刻可能立刻觸發一波密集 eviction。
- 代價（補一句）：這波突發 eviction 可能短時間內大量踢掉剛好還熱的 key，造成 promote 後短暫命中率下降；緩解 = promote 前先監控 replica 記憶體用量，設計 replica 的實體記憶體要比 `maxmemory` 留更多 headroom（呼應 1.2）。
</details>

## Part 3 — 收斂到 Distributed Cache 整體設計（20 分鐘）

把 Day 9（consistent hashing 分片）+ 今天（eviction + replication）拼起來，這就是 Mock #3 的骨架：

1. **分片層（Day 9）**：consistent hashing 把 key 分到 N 個 shard，用 virtual nodes 處理負載不均與異質機器。
2. **單 shard 內（今天 Part 1）**：每個 shard 自己有 `maxmemory` 上限 + 一個 eviction policy（預設建議 `allkeys-lru`，除非能證明存取均勻或能主動設 TTL）。
3. **單 shard 的高可用（今天 Part 2）**：每個 shard = 1 master + M replica，async replication，master 是唯一負責 eviction/expire 決策的節點、廣播 `DEL` 給 replica 保持一致；replica 預設唯讀、只服務讀流量分攤。
4. **故障處理**：master 掛掉 → promote 一個 replica → 新 master 開始自己跑 eviction；剩餘的 partial resync 機制讓其他 replica 不用整份重新同步。
5. **選型+代價一次講完（Part 1.1 句型）**：「我會用 N 個 shard、每 shard 1 master + 2 replica，async replication、master 端跑 `allkeys-lru`。代價是（a）master 掛掉到 promote 完成之間有一段時間該 shard 的計數/資料不可寫，（b）async replication 下 promote 可能丟失少量最新寫入。緩解：用 Sentinel/Cluster 自動 failover 縮短空窗，對容忍不了丟資料的 key 用 `WAIT` 換取更低（但非零）的丟失機率。」
