## Part 2 — Week 2 Building Blocks Cheat Sheet

### Rate Limiter 演算法比較

| 演算法 | 適用 | 代價 |
|---|---|---|
| Fixed window | 最省事 | 邊界突刺（兩個視窗交界可能瞬間 2 倍流量） |
| Sliding window log | 絕對精確 | 記憶體隨請求數線性成長 |
| Sliding window counter | 大規模、省記憶體 | 近似值（假設前視窗均勻分布，Cloudflare 實測誤差約 6%） |
| Token bucket | 允許可控 burst | 需要同時算「剩多少 token + 何時 refill」，原子性實作比純 counter 複雜 |
| Leaky bucket | 輸出速率絕對平滑 | 多次原子操作，高流量下鎖競爭重 |

### Distributed Rate Limiting

- 核心取捨：**狀態集中（Redis，準但有網路往返 + 單點）vs 狀態局部（各節點自算，快但總量最多超 N 倍）**——跟 CAP 同形狀。
- **Stripe 模式**：集中式 Redis + Lua script 做原子 read-check-write（或 `INCR`+`EXPIRE` 給只需遞增數字的演算法）+ **fail-open**（「rate limiter 的故障模式不該比它要防的問題更糟」）+ kill switch / dark launch 上線機制。四層架構：request rate limiter → concurrent requests limiter → fleet usage load shedder → worker utilization load shedder。
- **Cloudflare 模式**：anycast 讓同來源固定到同 PoP → 免跨 PoP 同步；PoP 內用 Twemproxy + consistent hashing 把計數分散到 memcached；選 sliding window counter 是因為協調成本最低（只需 `GET`+`INCR`）；決策非同步 + 本地快取降低延遲影響。
- 面試話術：地理局部 + 延遲敏感 → 局部計數；單 region + 計費相關 → 集中式 + fail-open。fail-open vs fail-closed 本身也要講代價（fail-closed 安全優先但放大故障半徑）。
- 來源：[Scaling your API with rate limiters — Stripe blog](https://stripe.com/blog/rate-limiters)、[Counting things: A lot of different, distributed, things — Cloudflare blog](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)

### Consistent Hashing

- 解決 `hash mod N` 的問題：N 一變，幾乎全部 key 重新映射；consistent hashing 只讓新增/移除節點影響環上一小段區間的 key。
- Virtual node：讓負載在環上分佈更均勻，也能依節點效能比例分配權重（效能 2 倍 → 2 倍 virtual node）。**跟「需要幾台實體機器」是兩個獨立維度**（Physical node 數量由容量+容錯算式決定；virtual node 數量決定既有節點間怎麼分才均勻，兩者互不取代，Day 11 已練熟）。
- 來源：[system-design-primer — Sharding](https://github.com/donnemartin/system-design-primer#sharding)、[The magic of consistent hashing — paperplanes.de (Mathias Meyer, 2011)](https://www.paperplanes.de/2011/12/9/the-magic-of-consistent-hashing.html)、[Consistent Hashing — Toptal Engineering Blog](https://www.toptal.com/big-data/consistent-hashing)

### Cache Eviction Policy

- Redis `maxmemory` 觸發後依 policy 淘汰：approximated LRU（抽樣 + 候選池）、approximated LFU（Morris counter + decay）等九種 policy，依存取模式（近期性 vs 頻率）選擇。
- 來源：[Redis 官方文件 — Key eviction](https://redis.io/docs/latest/develop/reference/eviction/)、[system-design-primer — Application caching](https://github.com/donnemartin/system-design-primer#cache)

### Replication for Cache

- Redis 走 async replication（sync 會等待 replica 確認，拖慢寫入延遲）。代價：master 掛掉時「已回應但未同步」的寫入會遺失；`WAIT` 可**降低（非消除）**這個機率，不是「確保一致性」（一致性指的是讀到的資料是否反映最新寫入，是不同的軸，Day 12 Part 1 片段3(b) 已修正這個用詞混淆）。
- Replica 預設忽略 `maxmemory`（避免淘汰掉還沒被讀取確認的資料），由 master 廣播 `DEL` 統一淘汰；promote 成 master 那一刻才開始自己算 eviction，可能觸發密集 eviction burst（Mock #3 的坑，Day 11 已完整分析）。
- 來源：[Redis 官方文件 — Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)、[system-design-primer — Replication](https://github.com/donnemartin/system-design-primer#replication)

## Part 3 — 容量估算練習

題目：500k active keys，每 value 平均 2KB，replication factor = 2，單機記憶體上限 32GB，寫入尖峰 QPS 50k，單機寫入上限抓 100k ops/s。求 (a) 總記憶體需求 (b) 至少要幾台 physical node (c) 寫入 QPS 會不會先於記憶體成為瓶頸。

### 第一輪（記憶體算錯，數量級差近 20 倍）

- 算出「40G」，實際算式「40,000 × 2 × 0.5M」把 `500k keys` 這個數字重複代入（`0.5M` 本身已經是 500k，又跟 `40,000` 相乘），導致單位混亂。
- 因為記憶體算錯到 40GB（超過單機 32GB 上限），連帶推出「至少 2 shard」的錯誤架構結論——**這是典型的「估算錯誤直接帶偏架構決策」案例**，跟 Week 1 Day 3 Q2 keyspace 算錯是同一種錯誤形狀（重複代入/單位混淆）。
- 同時「replication factor = 2」講成「1 master + 2 replica」（=3 份拷貝），跟 RF=2 慣例上「總共 2 份拷貝」的定義對不上。

### 第二輪（修正後）

- 正確算式：500,000 keys × (2KB value + ~80 bytes metadata ≈ 2.08KB) ≈ **1.04 GB**（單一份拷貝）；RF=2 → 總共 2 份拷貝 ≈ **2.08 GB**。
- 對比單機上限 32GB：2.08GB 只佔 ~6.5%，記憶體容量完全不是問題。
- 寫入尖峰 50k QPS < 單機上限 100k ops/s，寫入也不是瓶頸。
- 主動延伸：「master 掛掉、唯一 replica 被 promote 後系統會暫時缺乏 replica，可用性降低」→ 建議把 RF 提高到 3。**這個延伸跟 Mock #3 的「容量夠不夠 → 容錯夠不夠」正向習慣同一形狀，值得肯定。**

### 第三輪（修正「physical node 數量」的判斷維度）

- 出現的矛盾：算完「記憶體只需 1 台」後，又說「1 master + 1 replica」——master 跟 replica 必須放在不同實體機器才有容錯意義，兩句話互相矛盾。
- **正確心智模型（呼應 Day 11 Part 2 的 physical/virtual node 維度切分）**：physical node 數量由「容量算式」和「容錯算式」共同決定，取兩者中較大的數字。
  - 容量算式 → 1 台就夠（2.08GB ≪ 32GB）。
  - 容錯算式 → RF=2 至少 2 台，若採納 RF=3 建議則需 3 台（master + 2 replica，分散在不同機器）。
  - **容錯數字勝出** → 最終需要 **3 台 physical node**。

### 最終結論

- (a) 記憶體需求 ≈ 2.08GB（RF=2）／≈ 3.1GB（若採 RF=3）
- (b) Physical node 數：容量只需 1 台，容錯需求（RF=3、需分散在不同機器）需要 3 台 → **3 台**，這個數字由容錯決定，不是容量決定
- (c) 寫入尖峰 50k QPS < 單機上限 100k ops/s，無瓶頸，不需要為吞吐分片
