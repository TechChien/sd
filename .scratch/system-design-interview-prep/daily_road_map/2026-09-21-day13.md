## Part 1 — 即時通訊機制：Long Polling / WebSocket / SSE

### 1.1 三種機制的運作方式

| 機制 | 運作方式 | 連線型態 |
|---|---|---|
| **Long Polling** | Client 發請求，Server **不立刻回應**，held 住連線直到有新資料或 timeout 才回；client 收到後立刻發下一個請求 | 每次還是一次 HTTP request/response，只是拉長了等待時間；本質仍是 client 主動輪詢 |
| **WebSocket** | HTTP handshake 升級（`Sec-WebSocket-Key` / `Sec-WebSocket-Accept` header）後，變成**持久、全雙工**的單一 socket 連線 | Client、Server 都能**主動**在任何時間點發訊息，不需要對方先問 |
| **SSE（Server-Sent Events）** | 單向（server → client）的 HTTP 長連線串流，瀏覽器端有內建自動重連機制 | 只有 server 能推，client 不能透過同一條連線推回去 |

來源：
- [MDN — WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)：「makes it possible to open a two-way interactive communication session between the user's browser and a server... without having to poll the server for a reply」；handshake 機制與 header 定義。
- 綜合比較（primer 未涵蓋此主題，改用工程社群普遍認可的決策法則，來源：[Polling vs. Long Polling vs. SSE vs. WebSockets vs. Webhooks — AlgoMaster blog](https://blog.algomaster.io/p/polling-vs-long-polling-vs-sse-vs-websockets-webhooks)、[RxDB — WebSockets vs SSE vs Long-Polling vs WebRTC vs WebTransport](https://rxdb.info/articles/websockets-sse-polling-webrtc-webtransport.html)）。

### 1.2 決策法則（面試話術）

> 「只有 server 推 → 用 SSE；雙方都要推 → 用 WebSocket；沒有特殊限制的話，不要一開始就選 long polling。」

- **Long Polling 的代價**：每次「有新資料」到「下一次請求送達」之間有一段空窗；held 住的連線數量隨並發使用者線性成長，對 server 端連線資源（thread/fd）壓力大；且每次重新建立 request 有 HTTP header 開銷。
- **WebSocket 的代價**：需要維護大量長連線的狀態（stateful），連線跟哪台 server 綁定 → 影響水平擴展設計（需要 sticky session 或額外的訊息路由層，Week 3 Day 2-3 會處理「訊息要送到使用者實際連的那台 server」這個問題）；**MDN 明確指出標準 WebSocket interface 不支援 backpressure**——當訊息湧入速度超過應用程式處理速度時，會塞爆記憶體或讓 CPU 100% 忙碌。這個限制會直接連到 Part 2 的 message queue「為什麼需要 back pressure 機制」。
- **SSE 的取捨**：只需要標準 HTTP（不用額外 upgrade protocol），瀏覽器原生自動重連，但只能單向；適合「只需要監聽」的場景（儀表板、通知、log tail），不適合聊天室這種雙向即時的場景。

### 1.3 Chat System 的選型結論

**聊天室需要雙向（使用者送訊息、也要即時收到別人的訊息）且低延遲 → WebSocket 是核心選擇。**
- 代價：連線是 stateful，且不支援 backpressure，這兩點會成為 Day 2-3 設計「多台 server 之間怎麼路由訊息」與「怎麼防止訊息淹沒單一連線」的起點。
- 緩解方向（今天先點出問題意識，Day 2-3 深入）：
  - Stateful 連線 → 需要一層「connection registry」記錄 user 連在哪台 server（常見用 Redis 存 `user_id → server_id` 映射）。
  - 沒有 backpressure → 應用層自己控速，或訊息先進 message queue 緩衝，由 consumer 依自己的處理能力拉取（這正是 Part 2 的角色）。

## Part 2 — Message Queue 基礎

### 2.1 為什麼需要

> 「Asynchronous workflows help reduce request times for expensive operations that would otherwise be performed in-line.」

Message queue **接收、暫存、投遞訊息**：Producer（發送方）把工作丟進 queue 就可以立刻返回，不用等處理完成；Worker（消費方）從 queue 拉取訊息在背景處理。這把「產生訊息的速度」跟「處理訊息的速度」解耦（decouple）。

來源：[system-design-primer — Asynchronism](https://github.com/donnemartin/system-design-primer#asynchronism)

### 2.2 核心組成

- **Message Queue**：純粹負責「收、存、送」訊息，不執行任何業務邏輯。
- **Task Queue**（與 message queue 常一起被提到的近親概念）：接收 task 連同其資料，**執行**後回傳結果，通常還支援排程（scheduling）。
- **Back Pressure**：當 producer 產生訊息的速度長期超過 consumer 處理速度，queue 會無限增長 → 用**大小上限**擋住：queue 滿了就拒絕新訊息或回饋壓力給上游，維持「已經在 queue 裡的工作」有穩定的高吞吐與良好回應時間，避免整個系統被拖垮。這正好對應到 Part 1.2 WebSocket 沒有內建 backpressure 的缺口——訊息佇列是彌補這個缺口的標準做法之一。

### 2.3 什麼時候不該用非同步

> Primer 原文結論：「inexpensive calculations and realtime workflows might be better suited for synchronous operations」

聊天室裡「使用者傳一句話、對方要即時看到」是典型的 realtime workflow——**不代表聊天室不用 message queue**，而是要分清楚：
- **即時投遞路徑**（訊息從 A 的 client 送到 B 的 client）：延遲敏感，走 WebSocket 直接推送，不該卡在 queue 裡等。
- **需要保證可靠送達、離線使用者的訊息、跨服務通知（如推播）**：這些場景延遲容忍度較高，用 message queue 換取可靠性（Day 2 delivery guarantee 會深入這個分工）。

**面試話術**：主動點出「聊天系統不是單一路徑，而是即時路徑 + 可靠投遞路徑並存，兩者用不同機制，不能用同一套解法硬套所有情境」——這也是 Day 7 checklist「不過度設計」/「選策略要講代價」的延伸應用：不是每個訊息都該進 queue，要看場景需求。

## Part 4 — 練習題口說作答記錄與回饋

### 題 1 作答

> Client A publish message to message queue → message queue consumer receive → websocket or SSE → client B → client B gets notification。B 讀取訊息 → publish 一個 read event 到 message queue → consumer → websocket/SSE → client A → A 端顯示已讀狀態。

**回饋**：即時投遞路徑（A→B）的骨架正確，但有三處待補：
1. **狀態機不完整**：只用 read/unread 二態不夠，應為 `sent → delivered → read` 三態；delivered 是「B裝置收到」，read 才是「B真的看過」，兩者要分開記錄與呈現（單勾 vs 雙勾）。
2. **已讀狀態必須落地 DB**，不能只靠一次性的 WS/SSE 廣播——A 若當下離線，重連後仍要能查到「B 已讀到哪一則」。
3. **多裝置同步與批次已讀未提及**：B 同時登入多裝置時，任一裝置觸發已讀要同步給 B 自己其他裝置；已讀通常用「已讀到 messageId=X 為止」的游標式設計，而非逐則 publish read event，減少 MQ 流量。

### 題 2 作答

> (a) 發送端 publish 到 MQ，consumer 透過 WS 發給 B 並設定 ACK timeout，B 沒回 ACK 則判定離線，存入 DB（記錄 unread/read）。
> (b) 每次開啟 App 自動查詢是否有未讀訊息，有則顯示。

**回饋**：
- **(a) 用 ACK timeout 判斷離線的設計有陷阱**：網路延遲與真的離線很難即時區分，容易誤判。更穩妥的分層做法：
  - **連線層**直接用 WS 的 connect/disconnect 事件或心跳（heartbeat）判斷在不在線，不靠訊息 ACK 反推。
  - **訊息層**則不論在不在線，訊息一律先無條件寫入 DB（status=sent），在線就順便推播、離線就等下次同步——這樣邏輯更簡單，也不會因網路抖動誤判。
- **(b) 方向正確**（等同業界標準的「reconnect sync」），可以再具體化：客戶端維護 `last_synced_message_id`／`last_synced_timestamp`，重連或開啟 App 時呼叫 `GET /messages?since=...` 做**增量**同步，而非全量拉取；WS 只負責在線時的即時推播，sync API 是離線期間訊息的兜底機制。

### 題 3 作答

> 1. WebSocket 是 stateful session，用 sticky session 或把 session 存 Redis，讓 dispatcher 知道分配到哪台 server。
> 2. 大量訊息湧入時，WebSocket 沒有 back pressure，先讓訊息進 MQ 緩衝，由 consumer 分配。

**回饋**：這題答得最完整，緊扣 Part 1.3 的兩個限制（stateful、無 backpressure），只補兩點細節：
- **(1)** sticky session 的代價是該 server 擴縮容/重啟時，掛在上面的連線會被迫斷線重連；用 Redis 存 `user_id → server_id` 映射彈性較好，且是支援「A、B分屬不同 server 時如何互轉訊息」的必要基礎（而不只是負載平衡用途）。
- **(2)** MQ 緩衝解決的是「寫入端」的背壓，**推播端（WS 本身）仍可能因單一 server 連線數/頻寬打滿而成為瓶頸**；需要搭配依 user_id 分區的 consumer group（呼應 (1) 的 Redis 映射做正確路由）與必要時的推播節流/合併。
