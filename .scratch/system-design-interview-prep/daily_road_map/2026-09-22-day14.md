## Part 1 — Delivery Guarantee：三種投遞保證

### 1.1 三種保證的定義與機制

| 保證 | 定義 | 機制 |
|---|---|---|
| **At-most-once** | 訊息最多送達一次；系統故障時可能遺失，不會重送 | Producer「fire and forget」，不等 broker 確認，或只等 leader 確認；犧牲可靠性換取低延遲 |
| **At-least-once** | 訊息送達一次或多次；不會遺失，但可能重複 | Producer 沒收到 commit 確認就重送（resend logic）；為避免 broker 端重複寫入，用 producer ID + sequence number 做去重（idempotent producer，Kafka 自 0.11.0.0 起） |
| **Exactly-once** | 訊息恰好送達一次；不會遺失也不會重複讀到 | Producer 端用交易（transaction）確保訊息「複寫成功才算數」，重送時用 idempotency 覆寫而非重複；consumer 端把「更新 offset」跟「寫出結果」放進同一個 transaction |

來源：[Confluent — Message Delivery Guarantees](https://docs.confluent.io/kafka/design/delivery-semantics.html)

### 1.2 為什麼「端到端 exactly-once」在實務上很難、也不一定必要

- Exactly-once 的 transaction 機制通常只保證「broker 內部」的恰好一次（producer→broker→consumer 這段管線），一旦牽涉到**外部系統的 side effect**（例如 consumer 處理完訊息後呼叫另一個 API、寫另一個 DB），exactly-once 保證就會斷掉——因為「訊息處理成功」跟「外部呼叫成功」是兩個獨立的失敗點,無法用同一個 transaction 包起來。
- 業界更常見的實務做法是：**用 at-least-once 傳輸 + consumer 端做 idempotent 處理 = effectively-once**。
  - Idempotent Consumer pattern：consumer 收到訊息先檢查「這個 message ID 是否已經處理過」（存一張 `PROCESSED_MESSAGES` 表，`(subscriber_id, message_id)` 做 primary key），已處理過就直接丟棄（discard），沒處理過才真的執行業務邏輯，並在同一個 transaction 裡把 message_id 寫入。
  - 這樣即使 consumer 重複收到同一則訊息（at-least-once 的正常現象），實際效果等同只處理一次。

來源：[microservices.io — Idempotent Consumer](https://microservices.io/patterns/communication-style/idempotent-consumer.html)：「a consumer must be idempotent: the outcome of processing the same message repeatedly must be the same as processing the message once」

### 1.3 套用到 Chat System：今天的訊息投遞要選哪種？

呼應 Day 13 Part 2.3「即時路徑 vs 可靠投遞路徑」的分工：

- **可靠投遞路徑（訊息落地 DB、離線同步）**：選 **at-least-once + idempotent consumer**，不追求 broker 層的 exactly-once。
  - 具體設計：client 送訊息時帶一個**client 產生的 `message_id`**（例如 UUID，避免重送時 server 重新產生 ID 造成重複）；consumer 寫入 DB 時用 `message_id` 做 unique constraint，重複寫入直接被擋下（等同 Idempotent Consumer pattern 的 `PROCESSED_MESSAGES` 表，只是這裡直接用 messages 表本身的 unique key 承擔這個角色）。
  - 這解釋了 Day 13 題 1 回饋裡「已讀狀態必須落地 DB」的底層機制：DB 的 unique constraint 就是「effectively-once」的防線。
- **即時推播路徑（WebSocket push）**：可以接受 **at-most-once**——因為背後有 DB 已經保存訊息（1.3 上一點），就算這次推播漏了（WS 斷線瞬間），B 重連後靠 Day 13 題 2 提過的 `GET /messages?since=...` 增量同步補回,不需要為了這條路徑額外做重送保證,重送保證留給「寫入 DB」這一步就夠。

**面試話術**：「投遞保證不是全系統選一種，而是分层——資料落地的路徑要 at-least-once + idempotent，避免遺失;即時推播路徑可以退讓到 at-most-once,因為背後有可靠路徑兜底,不用重複做兩次保證。」

## Part 2 — Consistency Model 選擇

### 2.1 三種 consistency pattern（primer 原文）

| Pattern | 定義（primer 原文） | 代表系統 |
|---|---|---|
| **Weak consistency** | "After a write, reads may or may not see it. A best effort approach is taken." | memcached；適合即時性場景如 VoIP、視訊通話 |
| **Eventual consistency** | "After a write, reads will eventually see it (typically within milliseconds). Data is replicated asynchronously." | DNS、email；適合追求高可用的架構 |
| **Strong consistency** | "After a write, reads will see it. Data is replicated synchronously." | 檔案系統、RDBMS；適合有交易需求的場景 |

來源：[system-design-primer — Consistency patterns](https://github.com/donnemartin/system-design-primer#consistency-patterns)

### 2.2 跟 CAP theorem 的關係

- Primer 的 Availability vs Consistency：分散式系統在**發生 network partition 時**只能在 Consistency 跟 Availability 二選一（P 是必須接受的現實,不是可以選的那一項）。
  - **CP**：partition 期間寧可讓受影響節點的請求 timeout,也要保證讀到的資料是最新的。
  - **AP**：partition 期間永遠回應,但可能回應的是舊資料。
- Weak/eventual consistency 對應 AP 傾向；strong consistency 對應 CP 傾向。這不是「哪個比較好」,是「partition 發生時你要犧牲哪一邊」的權衡。

來源：[system-design-primer — Availability vs consistency](https://github.com/donnemartin/system-design-primer#availability-vs-consistency)

### 2.3 套用到 Chat System：不同資料該選哪種 consistency？

聊天系統不是只有一種資料,不同資料的 consistency 需求不同——這跟 Day 13 Part 2.3「不是每個訊息都該進 queue」同一種「分場景」思維：

| 資料/功能 | 建議 consistency | 理由 |
|---|---|---|
| **訊息本文（message content）** | 對**同一個 conversation** 要求 **strong ordering**（誰先誰後要一致），但不要求「全球所有 replica 立刻同步」的 strong consistency——用 eventual consistency + **per-conversation 順序保證**（例如訊息帶遞增的 sequence number,只在單一 conversation 範圍內保序,不需要跨 conversation 的全域順序） | 使用者在意「這個對話裡訊息順序對不對」,不在意「另一個地區的 replica 是否毫秒級同步」；要求全域 strong consistency 會犧牲可用性跟延遲,得不償失 |
| **已讀回條（read receipt）** | **Eventual consistency** | Day 13 題1回饋已提到用游標式（`read up to messageId=X`）而非逐則,本來就是「最終會同步到」的語意,不需要同步寫入等所有 replica 確認 |
| **線上狀態（online/offline presence）** | **Weak consistency** | 跟 primer 舉的 VoIP/視訊通話同類——狀態變化太快、太頻繁,使用者可以接受「看到的在線狀態有幾秒延遲」,追求 strong consistency 反而拖慢整個系統 |
| **帳號設定/封鎖名單等安全相關資料** | **Strong consistency** | 這類資料錯誤的代價高（例如封鎖了對方但因為 replica 沒同步,還是收到訊息）,值得犧牲一點延遲換正確性 |

**面試話術**：「Consistency model 不是整個系統選一種,而是按資料的『錯誤代價』分別選——訊息順序在單一對話內要保證,但不需要全域強一致；已讀、上線狀態可以接受最終一致甚至弱一致；安全相關資料才值得選強一致。」這跟 Day 13 弱點清單「容易漏抓系統的不對稱性」直接對應——這裡的不對稱性是「不同資料對 consistency 的敏感度不同」。

## Part 4 — 練習題口說作答記錄與回饋

### 題 1 作答

> 1. A pub message to message queue and change message status in db to 'sent'
> 2. consume and change message status in db to 'delivered'
> 3. consumer notifies B via websocket
> 4. B reads the message and pub 'read' event to message queue
> 5. consume and change message status in db to 'read'
>
> 步驟2、5使用 at-least-once + idempotent consumer，因為接收文本以及訊息狀態需要 strong consistency，保證資料有序性，資料不遺失。

**回饋**：管線拆解正確（sent → delivered → read 三態,呼應 Day 13 回饋），但有兩個問題：

1. **範圍漏了兩處**：步驟 1（寫入 `status=sent`）跟步驟 4（publish read 事件）也是「資料落地／狀態轉換」的一部分,同樣要 at-least-once + idempotent，不是只有 2、5。判斷標準應該是「這一步有沒有寫 DB 或改變系統狀態」，而不是「這是不是流程中間的某幾步」。你漏掉的正是唯一一個**沒有寫 DB**的一步——**步驟 3（WebSocket 推播）**——這才是今天教材裡「可以只用 at-most-once」的環節，你完全沒提到,等於漏答了題目的後半段（「哪個環節可以只用 at-most-once」）。
2. **【今日新增，優先處理】三個不同維度的概念被塞進同一句話**：「at-least-once + idempotent consumer」是**delivery guarantee**（解決訊息遺失/重複），「資料有序性」是**ordering**（解決順序問題），「strong consistency」是**consistency model**（解決 replica 間讀寫可見性）——這三者是三個獨立的軸,不是同一件事的三種說法。at-least-once + idempotent consumer 解決的是「這則訊息會不會遺失、會不會被處理兩次」，跟「訊息之間的順序」、跟「其他 replica 多快看到這筆資料」都沒有直接關係。今天教材 Part 1.2 只談 idempotency 解決重複寫入，並沒有提到 consistency model；你自己把兩個章節的詞彙揉在一句話裡了。這跟 spec.md 已記錄的「virtual/physical node 混淆」「CAS/WAIT 亂套用」是同一種模式的新變體：**看到相鄰主題的詞彙,習慣性把它們焊在一起講,而不是先確認彼此是否真的相關**。

### 題 2 作答

> (a) 怎麼處理訊息在群組聊天室呈現順序，對嗎? (b) consistency model如何影響訊息決定機制，對嗎?
>
> a. message queue 使用有序 queue，先到先顯示的方式
> b. 使用 Strong consistency，需要保證每一筆資料的順序以及處理完成狀態；使用 Eventual consistency，不保證資料有序性，但每一筆訊息最後都會處理；使用 Weak consistency，則可能會有資料遺失的風險。

**回饋**：Paraphrase 這次主動做了（略）,方向對,但覆述時把 (a)(b) 都簡化成單一句子,遺漏了「幾乎同時送訊息」這個關鍵限定條件——這正是 compound 題容易漏抓的「條件」而非「任務」本身，值得下次特別注意覆述時要包含觸發條件，不只是任務動詞。

- **(a) 「有序 queue、先到先顯示」不足以解決問題**：這句話假設了「queue 收到的順序 = 應該呈現的順序」，但兩個使用者幾乎同時送出時，訊息可能經過不同的 network path、打到不同的 broker partition/consumer，"先到 queue" 不代表 "先被使用者按下送出"，且分散式系統裡「先到」本身就是不可靠的判斷依據（這正是 Day 13 弱點清單提過的「不確定時硬套一個記得的詞彙」的變體——這次套的是「先到先顯示」這個直覺,但沒有先問「先到哪裡？誰保證到達順序反映真實順序？」）。今天教材 Part 2.3 給的正確機制是：**由單一權威來源（例如以 conversation_id 為 key 固定路由到同一個 partition/consumer）幫每筆訊息蓋上遞增的 sequence number**，順序由這個 sequence number 決定，不是由「誰先到 queue」決定。
- **(b) 再次出現題 1 的維度混淆**，且這次三句話各自都有事實錯誤：
  - 「Strong consistency 需要保證順序」——不對，strong consistency 講的是「寫完之後,任何 replica 讀到的都是最新值」，跟「多筆不同訊息之間的先後順序」是兩件事（一個系統可以是 strong consistency 但完全沒有跨訊息排序機制）。
  - 「Eventual consistency 不保證有序性,但每一筆訊息最後都會處理」——「最後都會處理」講的其實是 at-least-once 的「不遺失」保證，不是 eventual consistency 的定義（eventual consistency 講的是 replica 何時同步到最新值,不是訊息會不會被處理）。
  - 「Weak consistency 可能會有資料遺失的風險」——不對，primer 對 weak consistency 的原文定義是「reads may or may not see it，best effort」，講的是**讀到的資料可能不是最新**，不是「資料真的遺失」。這跟 delivery guarantee 裡的「遺失」是不同語意，混用會讓面試官誤以為你不清楚這兩個詞的差異。

### 題 3 作答

> 1. 會有類似情形發生可能因為連線到不同的伺服器，訊息狀態在資料庫不一致導致顯示上不一致
> 2. 將已讀回條發到 message queue, 更新資料庫。

**回饋**：第 1 點承認「會發生」且抓到根因方向（不同節點/replica 資料還沒同步）算對；但第 2 點只是把今天教材已經在用的機制（已讀回條走 MQ 更新 DB）重講一次，**沒有回答「這個代價你要怎麼緩解」**——面試官問的是「已讀狀態跳掉」這個**症狀**的緩解方式，不是問你已讀回條的傳輸機制本身。

**【修正】我原本在這裡給的回饋（單調遞增 seq/游標可緩解跳動）是錯的，已被你當場指出並更正**：你舉的情境是「replica A、B 網路分區，A 上已讀=已讀、B 上還是未讀，分區癒合後 B 同步成已讀，使用者畫面上看到未讀→已讀」——這個跳動方向本來就是**遞增**（未讀→已讀），monotonic cursor 的規則（`只在新值較大才更新`）完全不會擋下它，因為它符合遞增，不是我原本以為的「亂序倒退」情境。這兩者是不同的失敗模式：
- 亂序倒退（例如 read 事件 6 比事件 5 先到，游標一度往回跳）→ monotonic cursor 才擋得住。
- 分區造成的 replica 落後、癒合後才追上 → 這是 **eventual consistency 選型本身必然要付的視窗期代價，不是能靠更新規則消除的 bug**。monotonic seq 在這裡只負責「分區癒合時怎麼合併衝突」（取 seq 較大者為準，保證收斂到正確答案），並不能讓使用者感受不到跳動。
- 真正能緩解（不是消除）的做法：**sticky/read-your-own-writes routing**（同一 session 盡量固定路由到同一 replica，降低來回切換頻率）、**界定 replication lag 的上限（bounded staleness）**讓視窗期至少可預期。老實承認「這是選 eventual consistency 換可用性的必然代價，只能縮小視窗、無法完全消除，除非把這條路徑換回 strong consistency（但那會犧牲已讀回條這種高頻寫入的效能）」才是面試中正確且誠實的答法。

這次修正本身也值得記錄：**你能對照自己給的具體情境,發現我提出的機制其實答非所問，並準確指出「這個跳動方向是遞增的」這個關鍵細節**——這正是 spec.md 弱點清單一直在要求你培養的「說出 cost/mitigation 前檢查兩者是否真的邏輯相關」的能力，這次是用在檢查**我的**答案上，是好的遷移信號。

## 今日弱點清單增修

- **【今日新增，最高優先，全新模式】把 delivery guarantee／ordering／consistency model 三個獨立維度混為一談**：三題作答都出現「用 strong/eventual/weak consistency 的詞彙去解釋『訊息會不會遺失』或『訊息順序對不對』」，但這兩件事在今天教材裡分別屬於 delivery guarantee 和 ordering，跟 consistency model（replica 間讀寫可見性）是三個獨立的軸。跟既有弱點「virtual/physical node 混淆」「CAS/WAIT 亂套用」同一種模式（相鄰主題詞彙互相借用),但這次是**三個維度同時混**，範圍更大，建議下次 mock interview 前先自我測驗：給一個情境,要求分別用「會不會遺失/重複」「順序對不對」「多久看到最新值」三句話分開回答，練到不再需要提示。
- **【今日新增】題目要求「分別說明兩種情境」時,只答出其中一種，漏答另一半**：題 1 只講了「哪裡要 at-least-once」，完全沒提「哪裡可以只用 at-most-once」；跟 Day 12 的「內容正確≠檢查動作已內化」類似，是「看到 compound 問題,回答完第一部分就停下,沒有主動核對是否還有第二部分未答」。建議比照 paraphrase 的作法，回答前先確認自己列出了問題要求的**每一個**子項目。
- **【今日新增】把面試官追問的「症狀緩解」答成「重複描述既有機制」**：題 3 面試官已經預設了你的原始設計（已讀走 MQ 更新 DB），追問的是這個設計仍會出現的**副作用**要怎麼處理，直接重述原始機制等於沒回答到追問點——跟 spec.md 已有的「選定策略時只講優點、不主動點出代價」屬同一類「沒聽出面試官問的是下一層問題」，只是這次問的是「代價」的下一層（代價的具體症狀 + 緩解），需要練習分辨「你在被問設計本身」還是「你在被問這個設計的某個已知限制」。
- **今日具體技巧補強（已修正）**：題 1、2 缺的解法是「用單調遞增的 sequence number／游標決定順序,不要用到達時間判斷」；但題 3 的情境（replica 分區癒合造成的已讀跳動）**不是同一個問題**——那是 eventual consistency 選型必然的視窗期代價，monotonic seq 在那裡只負責「分區癒合時怎麼合併衝突」，不能讓使用者感受不到跳動，緩解要靠 sticky routing／bounded staleness，或誠實承認代價無法完全消除。這個修正本身是我（教學端）先前把兩種失敗模式（亂序倒退 vs replica 落後）混為一談,被你用具體情境當場指出並更正——**你在這裡示範了「檢查 cost/mitigation 是否邏輯相關」用在檢查別人（我）的答案上，是正向遷移訊號，值得保留**。
